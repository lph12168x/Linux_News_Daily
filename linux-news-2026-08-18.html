Linux 7.3 将落地 vRAM 显存管理改进（Valve Natalie Vock·有限显存游戏体验）
图形 计算
Valve Linux 图形团队工程师 Natalie Vock 早前提出的「改善低显存系统 Linux 游戏体验」补丁，其内核视频内存管理部分已排入 DRM-Next，将在未来约两周内的 Linux 7.3 合并窗口合入。Vock 今日发布长篇博客说明最新进展：围绕显存管理、eviction（驱逐）处理与实测做了大量工作——以《印第安纳琼斯：大 Circle》为例，在仅 8GB vRAM 的卡上强行拉满设置、试图占用 9GB 显存（超额 1GB），游戏依然相当可玩。该改进已随 SteamOS 内核（stable 与 preview 双通道）上线；更多上游化改进仍在推进，测试补丁分支为 vramstuff-rebase。
关注理由：对显存紧张（8GB 及以下）的 Linux 游戏玩家，vRAM overcommit（超额提交）体验的改善是直接利好：以往显存用尽极易触发严重掉帧甚至崩溃，而 Valve 的这套内核级显存管理让驱逐到系统内存的降级更平滑。这延续了 Valve 持续投资 Linux 图形栈（RADV、DRM 调度、TTM）的一贯路线，且已先在 SteamOS 验证。

FFmpeg 落地 H.265/HEVC Vulkan 编码性能优化（与 H.264 编码速度持平）
图形
FFmpeg Git 今日合并优化补丁，加速 hevc_vulkan（H.265/HEVC 的 Vulkan 编码路径）。补丁沿用了此前 h264_vulkan 的部分调优：开启 ALLOW_ENCODE_PARAMETER_OPTIMIZATIONS 会话标志、在 CTB≥32 时用 min CU 16×16、修复 max_transform_hierarchy_depth_inter 赋值，并在应用 GetEncoded SPS 反馈时同步被覆盖字段。实测（1080p testsrc2、quality 1、1000 帧）：优化前 hevc 约 200–317 fps、明显慢于 h264；优化后 hevc 289/325/358 fps，h264 288/317/359 fps，二者达成速度持平。
关注理由：Vulkan 视频编码（尤其是 HEVC）在 Linux 上的实用性与性能一直是短板。FFmpeg 让 HEVC Vulkan 编码从明显落后于 H.264 追赶到速度持平，意味着在 AMD/Intel/Apple 等支持 Vulkan 视频编码的 GPU 上，开源多媒体管线能以更低开销完成 H.265 编码，利好录屏、串流与视频生产。

研究论文：把 Rust 卸载到 GPU 可兼顾高性能与内存安全（LLVM Offload）
计算 图形
一篇由 Manuel S. Drehwald 等人发表的新论文，研究基于 LLVM Offload 基础设施用 Rust 编写 GPU 内核：在保留 Rust 内存安全等优势、让大多数 GPU 内核免于裸指针的同时，性能仍可与手写的原生 AMD HIP / NVIDIA CUDA C++ 内核竞争——多数测试表现接近、互有胜负。前端被视为「安全」，相关工作全部位于 LLVM 后端与 Rust 编译器中；研究者也指出后续仍有代码生成与 IR 差异等性能提升空间。论文见于 arXiv（2608.13759），上游跟踪见 Rust-Lang ticket #131513。
关注理由：长久以来 GPU 计算内核几乎被 CUDA/HIP（C++）垄断，内存安全是其痛点。该论文证明「安全 Rust + LLVM Offload」能在不牺牲太多性能的前提下写 GPU 内核，若上游化落地，将为 Linux 上的 GPU 计算带来更稳健、更现代的编程模型，对 AMD ROCm 与 NVIDIA CUDA 生态均有长期意义。

AMD 着手新后端：改善 ROCm 计算在 QEMU/虚拟机中的 GPU 虚拟化
计算
AMD 工程师 Honglei Huang 发起讨论，为 QEMU 下的 ROCm GPU 计算开发全新后端。现有方案借 Virglrenderer 的 VirtIO GPU context 类型、与显示路径共享，遇到诸多障碍：许多加速器没有显示引擎、计算上下文与显示路径争用导致显示卡顿、且计算通常需要比渲染模型允许的更多显存访问、ROCm 栈与渲染模型难以契合。AMD 因此计划实现专用于计算的 headless VirtIO GPU 实例，并开发一个由 QEMU 进程内加载的开源 ROCm 后端库，未来随 ROCm 栈分发。现有 ROCm native context（Virglrenderer MR #1568）尚未合入主线。
关注理由：GPU 虚拟化（在 VM 中跑 ROCm 计算）是云、CI 与隔离部署的关键场景。AMD 现有方案因与显示路径耦合而受限，新后端把计算独立为 headless VirtIO 实例、并提供进程内 ROCm 后端库，将显著提升虚拟机内 AMD GPU 计算的可用性与稳定性，利好想在大内存 EPYC 服务器上做 GPU 虚拟化部署的用户。

KTransformers 0.7 扩展 AVX-512 支持：利好 AMD EPYC（Zen 4/5/6）服务器 LLM 微调
计算
异构 LLM 推理与微调优化框架 KTransformers 发布 v0.7：现在无需依赖 AMX 即可获得完整的 AVX-512 LoRA 微调支持。这一「仅 AVX-512、无需 AMX」的路径直接利好拥有优秀 AVX-512 但缺少 AMX 的 AMD EPYC Zen 4 / Zen 5 / Zen 6 服务器，以及 Sapphire Rapids 之前带 AVX-512 的老款 Intel Xeon。运行时自动选择恰当的 CPU 实现，使 MoE 专家训练能在更广泛的大内存服务器上进行。0.7 还新增 VLM 微调支持、原生 FP8 LoRA、改进的 DeepSeek V4 部署与 CPU 激活复用。
关注理由：本地/私有化 LLM 推理与微调正快速普及，而 AMD EPYC 服务器常因缺少 Intel AMX 在相关框架中处于劣势。KTransformers 0.7 用纯 AVX-512 路径补齐这一短板，让 Zen 4/5/6 大内存服务器也能高效跑 MoE 微调，是 AMD 平台 CPU 侧 AI 计算可用性的实质提升。
