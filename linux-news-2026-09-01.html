AMD 更新 UALink 内核补丁 v2：为 Helios 平台的 UALoE 铺路，目标 Linux 7.4
计算
AMD 于 8 月内两度提交大规模 UALink（Ultra Accelerator Link）主线补丁集，本月底放出 v2 更新版。UALink 是用于在 scale-up pod 内互连 GPU 与其他 AI 加速器的开放标准高速互连协议。AMD 当前落地的重心是 UALink over Ethernet（UALoE），服务于基于 Instinct MI455X + 第六代 EPYC「Venice」+ Pensando AI NIC 的新一代 Helios 服务器，并已接入 AMDGPU 内核驱动。
v2 的两处关键变化：①修复 32 位内核构建；②放弃此前基于 sysfs 的配置 API，改为先依赖带外（out-of-band）工具完成 UALink 配置管理。补丁规模为 95 个补丁的 v2 系列（UALink 基础设施），随后又追加了带更新文档的 series 2 v2 补丁。
排期上，这批补丁已赶不上 Linux 7.3 窗口，最早有望随 Linux 7.4 进入主线；短期内的 Helios 交付预计仍依赖打了补丁的发行版内核。
关注理由：开放加速互连的主线化是 AI 基础设施最值得跟踪的主线之一：UALink 一旦进内核，意味着 scale-up 域的加速器互连不再被私有协议锁死，驱动 / 运行时 / 编排都能复用通用内核设施。对做 NPU、RDMA 与加速器软件栈的团队，这里有两点直接参考：一是「先带外工具、后内核 API」的渐进式上游策略（降低早期 API 固化风险）；二是 UALoE 把 UALink 承载在以太网上，它与 RoCE / UEC 生态的边界划分值得持续跟踪。

Mesa 26.3 换上自定义归并排序：BVH 构建更省显存，小场景光追收益明显
图形
Valve Linux 图形团队的 Natalie Vock 为 Mesa Vulkan 驱动重写了 Morton code key 的排序路径。Morton 码把 3D 点坐标按位交错成 1D 整数，是 BVH（层次包围盒）构建与 GPU 并行度的基础数据结构——此前 RADV（Radeon）、ANV（Intel）、Turnip（Adreno）与 Lavapipe 共用同一套排序实现。
Vock 发现既有排序存在低效点，改为自定义 merge sort，专为小数据集优化：
· 单次 dispatch 内完成，无需中间 barrier；
· 与 AS build 代码更紧耦合，省掉一次「写出未排序 key → 读回」的显存往返；
· 小问题规模（RADV subgroup=64 时 <512 元素）可在 shared memory 内生成并排序，只有写回结果时才接触 VRAM。
原话是：大数据集下略逊于 radix sort，但对小问题「absolutely eviscerates radix sort」。该改动经过约三个月测试与修 bug，上周已合入 Mesa 26.3，惠及所有开源 Vulkan 驱动（MR 41549）。
关注理由：BVH 构建吞吐是光追性能的隐性瓶颈，尤其在小场景、动态场景与每帧重建加速结构的负载下。这次优化的价值不在峰值数字，而在把排序从「显存往返」拉回「共享内存 + 单次 dispatch」——这类降低 VRAM 流量与 barrier 的实现手法，对自研光追管线、加速结构构建器以及 GPU 上的小规模排序原语都有直接借鉴意义，也再次体现 Valve 对 Mesa 通用计算路径（而非只服务 Steam Deck）的持续投入。

NVIDIA 提交调度器补丁：Olympus SMT 首选兄弟核，GEMM 再提至约 10.1 TFLOP/s
计算
NVIDIA 工程师 Andrea Righi 向 LKML 提交新调度器补丁系列，为 NVIDIA Vera 的 Olympus 核心建立「首选 SMT 兄弟核」。Olympus 以两个对称 PE（processing element）实现 SMT：仅一个 PE 活跃时核心处于单线程模式，该 PE 可独享全部核心资源；两个 PE 同时活跃则进入双线程模式共享资源。
Olympus 对兄弟核的短暂激活格外敏感——从双线程模式退回单线程模式并非立即完成，需要一段确认间隔（实测 Vera 系统上为 10 Ki cycles）。此前已合入 Linux 7.3 的提交 293f9611ae735（NOHZ 负载均衡偏好完全空闲核）已阻止空闲负载均衡无谓唤醒忙碌 PE 的兄弟核，但普通任务放置仍可能来回切换活跃 PE，使核心长期卡在双线程模式。
本系列通过 SD_ASYM_PACKING 把 PE0 设为 Olympus 核心的首选兄弟核，并让 CFS 的空闲选择路径感知非对称 SMT 优先级：先按既有规则挑空闲核心，再在核内选最高优先级的可用兄弟核。
实测（双节点 Vera，NUMA node 0 的 88 物理核跑 88 线程单精度 GEMM）：9.4 TFLOP/s → 约 10.1 TFLOP/s，且多次运行更稳定（负载稳定落在 PE0、PE1 保持安静）。叠加 7.3 那一次改动，该基准已从 6.2 → 9.2 → 10.1 TFLOP/s。
关注理由：这是「调度器微决策 = 数十个百分点算力」的教科书案例：同一份 GEMM 代码、同一颗 CPU，仅靠任务放置策略就累计提升约 63%。对 HPC 与 NPU 软件栈有两点启示：其一，SMT 拓扑敏感型核心（以及异构核、big.LITTLE、低功耗核）必须在调度层显式建模，否则纸面算力会被兄弟核争抢吃掉；其二，能力 / 优先级感知的空闲核选择这套框架（SD_ASYM_PACKING + 非对称 SMT）是通用机制，任何自研加速器的伴生 CPU 或异构核布局都可复用，不必重造调度器。

NVIDIA VA-API 驱动 0.0.18：修复 HEVC 解码瑕疵，Chrome/Chromium 在直接后端上可用硬解
图形
第三方开源项目 NVIDIA VA-API Driver（在 NVIDIA 的 NVDEC 接口之上实现 VA-API）发布 v0.0.18。由于官方 NVIDIA Linux 驱动栈长期是唯一不支持 Video Acceleration API 的厂商栈，这个社区实现一直是 Firefox 等仅支持 VA-API 的应用在 NVIDIA 硬件上获得 GPU 视频解码的主要途径。
v0.0.18 要点：· 修复 HEVC 解码伪像；· Chrome/Chromium 硬件解码在「直接后端（direct back-end）」上正常工作——这对 Wayland 与 ANGLE-on-Vulkan 场景尤为重要；· 其他多项修复与改进。该项支持部分借助 Claude Fable 5 做 bug 定位、Opus 协助实现完成。
展望：基于 VA-API 的 NVENC 编码支持已有 draft PR（#427），但尚未合入本次发布。另需留意 Firefox 自 153 起已开始实验性支持 Vulkan Video 解码，长期看会与 VA-API 路线并存。
关注理由：视频编解码是 Linux 桌面与边缘场景里最容易被忽视的功耗与体验短板。Chrome/Chromium 在 Wayland + ANGLE-on-Vulkan 下打通硬解，直接影响浏览器播放的 CPU 占用与续航；而 NVENC 编码一旦补上，VA-API 侧能力才真正与 NVIDIA 官方栈对齐。对做显示 / 多媒体栈的团队，这条线还揭示了一个趋势：Vulkan Video 正在成为跨厂商的统一解码抽象，VA-API 与它的分工会在未来一两年持续演进，值得提前布局。

AMD 提交 Zen 6 客户端 EPP 调校补丁：确认「性能 / 效率 / 低功耗」三核心类型
计算
在下一代 Ryzen Zen 6 客户端处理器上市前，Mario Limonciello（superm1） 向 LKML 提交了 Zen 6 客户端 ACPI EPP（Energy Performance Preference）调校补丁。Zen 6 客户端平台对 EPP 的用法与既有 Ryzen 世代不同，需要新的调校值才能保证 Linux 下的性能与功耗表现。
补丁分两部分：①重构 AMD P-State 驱动，引入按 SoC、按核心类型（per-core-type）的 EPP 调校框架，同时兼容现有与未来产品；②为 Zen 6 添加调校值，覆盖不同核心类型 × 四种偏好模式（performance / balance performance / balance power / power）。
重要信息点：补丁硬确认了 Zen 6 具备 performance、efficiency（dense）与 low-power 三类核心——其中低功耗核类型是 Linux 7.3 刚加入的新分类，此前仅停留在传闻层面；同时确认 Zen 6 客户端为 Family 1Ah，型号包括 0x80、0x81、0x84、0x85、0xe0。因不属于 fix，预计要等到 Linux 7.4 周期合入（或由发行版内核反向移植）。
关注理由：对调度与功耗建模而言，「核心类型」正在从两级（性能 / 能效）走向三级，这会直接冲击任务放置、能耗感知调度（EAS）与整机功耗预算的策略设计。Zen 6 的 EPP 调校框架按「SoC + 核心类型」参数化，是应对未来更碎片化拓扑的必要抽象——做异构调度与 NPU 伴生调度的团队可以直接照搬这个分层思路。另外，新平台首发时若内核未跟上调校值，性能与续航可能明显打折，这也是评估「新硬件 + Linux 发行版」就绪度的关键检查项。

Apple Silicon USB4/Thunderbolt 支持提交上游：M1/M2/M3 的 19 个补丁进入评审
显示
Apple Silicon Linux 主力开发者 Sven Peter 向 LKML 提交了 19 个补丁，为主线内核上的 M1 / M2 / M3 SoC 启用 USB4 / Thunderbolt 支持。此前该能力只在 Asahi Linux 的下游分支中提供，上游化进程已持续相当长时间。
技术难点在于 Apple 的设计：每个支持 USB4 的 Type-C 口都带一个 ACIO（Apple Converged I/O）块，内含一颗 Cortex-M3 协处理器与实现 USB4 router 的硬件；NHI 与 DART IOMMU 也在该块内，且 SoC 总线只在协处理器运行时获得一个 16 MiB 的 MMIO 窗口，而非把设备独立暴露出来。
当前能力与限制：仅支持 XDomain 连接与 USB3-over-USB4 隧道；PCIe 隧道与 DisplayPort 隧道尚未支持（需更多逆向工程）；不支持挂起，且在存在活跃连接时必须阻止挂起，否则恢复时会触发 SError。补丁已加入 M1/M2 设备树节点，M3 节点待其余栈上游后补上——但 Thunderbolt/USB4 代码已在 M3 上实测通过。
关注理由：对关注显示栈的人来说，关键在「DisplayPort 隧道还没有」——这意味着 Apple Silicon 上通过 USB-C / 雷雳外接显示器这条路尚未打通，是 Asahi 类平台走向日常可用的最后几块拼图之一。同时，ACIO「协处理器 + 受限 MMIO 窗口」的设计，也是带固件的 I/O 复合体如何在 Linux 下建模的典型案例：需要先拉起协处理器再枚举子设备，与自研加速器的上电 / 初始化流程有不少共通之处，值得作为驱动架构参考。
