DLSS5VKLayer 把 NVIDIA DLSS 5 接入原生 Linux 游戏与 Steam Play（Proton）
图形 计算
一个新开源项目 DLSS5VKLayer 提供 Linux Vulkan 层，让原生 Linux 游戏与 Steam Play（Proton）Windows 游戏都能实验性用上 NVIDIA DLSS 5。做法是把 Windows 的 NGX 神经渲染助手跑在 Wine/Proton 下，该隐式 Vulkan 层经 IPC 把渲染帧传给它、再把 DLSS5 后的帧回灌到 Vulkan swapchain；并用 NVIDIA Optical Flow 生成向量消除注入 DLSS 5 后的抖动/闪烁，可选启用 NVIDIA Smooth Motion。仍须 NVIDIA 官方驱动 + 自行提供 NGX DLL。
关注理由：对做图形/显示的团队，这是「Linux 上吃 DLSS 超分」的又一条非官方但可用的路径——核心是 IPC 把帧交给外部 NGX 推理再回灌 swapchain 的 Vulkan 层方案，可对照我们在加速器上「推理前后处理与显示链路解耦」的思路；同时它依赖 Optical Flow 做向量稳定，提示做 AI 超分时运动向量质量直接决定伪影，与 zeus 上超分/插帧的质量评估要点一致。

KDE KWin 合入 Wayland commit-timing 协议：视频播放与 Adaptive-Sync/FreeSync 时序可控
显示
KDE 开发者 Xaver Hugl 历时半年的合并请求终于合入 KWin 最新开发分支，支持 Wayland 的 commit-timing 协议。该协议允许应用设定合成器「最早可应用该 commit 的时间」，视频播放器可提前排帧、Adaptive-Sync 下更好控制刷新率；也是 Mesa Vulkan 驱动支持 VK_EXT_present_timing 的前提，对 VKD3D-Proton / Steam Play 很重要。恰逢 Plasma 6.8 Beta 1（9/10）与分支点，赶在 6.8 稳定前落地（GNOME Mutter 早在 Wayland Protocols 1.38 / 2024 末已支持）。
关注理由：对做显示/合成器的团队，commit-timing 是「应用与合成器对帧呈现时间达成共识」的关键协议——视频播放防撕裂/卡顿、Adaptive-Sync 下稳定刷新率都靠它；且与 VK_EXT_present_timing 直接挂钩，意味着 VKD3D-Proton 这类 D3D12→Vulkan 翻译层能拿到精确呈现时序。可对照我们在 zeus 显示管线上「呈现时序由谁主导、如何回传」的设计，避免合成器与应用各自为政造成抖动。

新补丁为 AMD Radeon（AMDGPU）带来 HDMI 1.4 3D 模式：frame packing / 上下 / 左右
显示
独立开发者 Adrian Betschart 提交 3 个补丁（约 60 行新代码），为 AMDGPU 内核驱动补上 HDMI 1.4 3D 输出（frame packing、top-and-bottom、side-by-side）。DRM EDID 解析器其实早已从 HDMI VSDB 取出 3D 信息，但 AMDGPU 一直没利用（Intel i915 早在 2012 就用上了）。方案最简洁：源端把双眼打包进一帧、显示核当普通 2D 扫描输出，仅 HDMI vendor infoframe 带 3D 标识；并在 top-and-bottom 的 vendor infoframe 加 3D_Ext_Data 字节（否则 JVC D-ILA 投影不进 3D）。已在 Radeon RX 7600（Navi 33, DCN 3.2.1）驱动 JVC DLA-RS4100、Kodi(LibreELEC, GBM) 为源、7.2.3 内核上验证 1920x1080p24 RGB 12bpc 双眼几何正确。
关注理由：对做显示/EDID 的团队，这条是典型的「能力探测已有、驱动没接」案例：EDID 的 HDMI VSDB 早已给出 3D 信息，AMDGPU 拖了十余年没用——提示做显示器能力清单时要把 VSDB 里的 3D/VRR 字段真正消费起来；且「补 3D_Ext_Data 字节否则特定投影不进 3D」说明 vendor infoframe 的边角字节常决定功能能否真正启用，与 FreeSync 的 VSDB 解析修复如出一辙，是显示兼容的共性坑。

DirectX 后端在 LLVM 升为官方目标：clang-dxc 默认启用、DXIL 编译进主线
图形 计算
过去四年微软推动的 LLVM DirectX 后端（把 LLVM IR 降到 DirectX 中间语言 DXIL，供 Windows DirectX 12 图形驱动执行）从此前实验性目标升为 LLVM 官方目标。微软 HLSL 编译器工程师 Farzon Lotfi 的提交把后端移出 experimental 并加入 clang-dxc 前端；自明年 LLVM 24 起 clang-dxc 与 HLSL 支持默认开启。微软后续重点将转向图形与光追 shader、最新 Shader Model，并进一步收紧 Clang HLSL 前端与后端 Codegen 的集成。
关注理由：对做图形/编译栈的团队，LLVM DirectX 后端成为官方目标意味着「用 LLVM 基础设施编译 DXIL shader」有了稳定、默认的入口，clang-dxc 开箱即用——这直接影响跨平台 shader 工具链与 Proton/VKD3D 生态的底层编译能力；也提示 DXIL 与 SPIR-V/Vulkan 两条 shader 中间表示的工具链正在各自成熟，做跨图形 API 的 shader 移植/验证时要同时跟踪两边进展。

AI 写出「不少丑陋代码」却揪出 Linux 内核编译瓶颈：全模块构建快约 36%、增量最高 70%
计算 内核
ARM Linux 工程师 Lorenzo Stoakes 用 LLM 辅助定位并修复内核构建的单线程瓶颈，提交 23 个补丁「显著加速内核构建」。他坦言 LLM 生成了大量代码、不少很丑陋，由他逐处审计、重写与修正；LLM 还编排了构建/测试/调试/分析。核心是把 Kbuild、kallsyms、modpost、objtool、mksysmap 及 Rust 构建系统等处的单线程任务并行化。实测全模块构建约快 36%、增量构建最高快 70%、noop 构建最高快约 90%，跨硬件与配置一致；每提交带 Assisted-by 标签，待评审后有望进主线。
关注理由：对做计算/构建系统的团队，这条是「AI 定位瓶颈 + 人审代码」的务实范本：36%~90% 的构建提速来自把单线程环节并行化（Kbuild/modpost/objtool 等），与我们在加速器上「把串行预处理/编译/链接打散并行」的思路一致；同时提示「LLM 产码需人审、性能须手工核」是底线——可借鉴其把构建 profiling 交给 AI 编排、正确性由人把守的分工，用于我们自己的构建/CI 提速。
