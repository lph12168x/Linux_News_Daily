Intel 把 CMRR 内容匹配刷新率推进到 Linux 7.4：Xe3 / Panther Lake 及更新默认启用，视频帧率更稳
显示 图形
Intel 工程师正把 CMRR（Content Match Refresh Rate，内容匹配刷新率）的启用工作排入 DRM-Next、瞄准 Linux 7.4。CMRR 是 Xe2 Lunar Lake 硬件首次引入的能力，相较普通 VRR / Adaptive-Sync 能更精准地把面板刷新率匹配到视频或内容帧率，目标是播放时不再卡顿或掉帧。
此前 CMRR 分数时序代码被永久禁用、仅限嵌入式 DisplayPort（eDP）、且靠启发式猜测何时走分数时序路径；新补丁修复了这些短板，并新增一个临时性的 DebugFS 控制接口（每-CRTC 文件，以毫赫兹精度指定目标刷新率与视频时序分母），待未来用户态 API 成型后替换。本期默认启用范围对应 Intel Display IP v30 及更新，即 Xe3 / Panther Lake 及更新硬件。该 pull 还顺带把 DG2 多协议 PLL 代码迁入 DPLL 框架、修 DP-HDMI PCON DSC 等。
关注理由：CMRR 填补的是「视频 / 内容」场景下 VRR 的最后一公里——普通 Adaptive-Sync 对固定帧率视频并不理想，CMRR 直接按内容帧率锁定面板，对视频播放、会议、串流等是实打实的体验提升。对做显示/图形驱动的同学，这里有两个可借鉴点：其一，新硬件能力从「补丁存在近两年」到「真正默认启用」往往要跨过 eDP-only、启发式、缺少用户态 API 等多道坎，CMRR 的演进是完整范本；其二，Intel 用每-CRTC DebugFS 接口作为用户态 API 成型前的过渡，是内核图形驱动「先暴露控制、后定稳定 ABI」的常见节奏。这与团队在 zeus 架构上「先打通能力、再固化接口」的思路一致。

Mir 2.29 发布：新增 xdg-dialog-v1 等 Wayland 协议、单表面截图与屏幕捕获源，迁移 C++26 并弃用 EGLStream
显示
Canonical 的 Mir 2.29 合成器发布，面向基于 Mir 构建 Wayland shell 的场景带来协议与功能扩充。本期新增 xdg-dialog-v1 协议（让应用告知窗口管理器某窗口是对话框，其他主流合成器已支持），以及 ext_foreign_toplevel_image_capture_source_manager_v1——允许客户端为指定顶层应用窗口创建图像捕获源，服务于录屏 / 屏幕捕获等用途。
Mir 2.29 还支持对单个 surface 截图、其 wl_region 实现现能处理 add 与 subtract、并新增触摸模拟器把鼠标点击/拖拽映射为触摸事件。工程侧：代码库迁移至 C++26、弃用 EGLStream、用 DMA-BUF 取代 wl-drm、并移除其他废弃 API，外加大量 bug 修复。
关注理由：Mir 虽非桌面主流，但它是 Wayland 协议落地的「试验田」之一——xdg-dialog-v1 与顶层窗口捕获源这类协议，正是屏幕共享、远程桌面、录屏工具在 Wayland 下能否顺畅工作的关键拼图。对做显示栈的团队，「弃用 EGLStream、全面转向 DMA-BUF」是这几年 Wayland 生态的统一方向（XWayland 26.1 也移除了 EGLStream），值得对照自身合成器是否已经切干净；而用自有 IR/运行时替代厂商私有路径（此处是 C++26 现代化 + DMA-BUF 优先）也是可借鉴的工程取舍。

NVIDIA 以 129.3 亿美元收购 Hugging Face：承诺保持开放平台、多云多加速器、不绑定 NVIDIA 计算
计算 NPU
NVIDIA 正式宣布以 129.303 亿美元收购 Hugging Face。Hugging Face 将继续作为分享大语言模型与数据集的平台存在。Jensen Huang 在公告中明确保留其开放平台属性：开发者可自行选择模型、框架、云与推理服务商、计算平台；NVIDIA 计算并非在 Hugging Face 上构建或部署的必需条件，平台继续支持跨生态的开源/开放权重模型、以及多云多加速器开发部署。
NVIDIA 表示将强化 Hugging Face 的基础设施、扩大全球开发者与组织的 AI 可及性。
关注理由：这是 AI 基础设施层的一次重大整合——Hugging Face 是 Linux 上本地推理（vLLM、llama.cpp、Transformer / Diffusers 等）事实上的模型与工具分发中枢。对做 NPU/加速器与 RDMA 计算栈的团队，关键点在于黄仁勋的「不绑定 NVIDIA 计算、支持多加速器」承诺：若兑现，意味着在 Hugging Face 上部署的负载仍能平滑落到 AMD / Intel / 自研加速器（包括 zeus）上，不会因收购而被锁进 CUDA 生态。这关系到团队未来「模型与运行时分发渠道是否保持硬件中立」的判断，值得持续跟踪收购后的实际工程动作（而非仅看表态）。

Amazon Linux 2027 公测：基于 Linux 7.1、x86-64-v3、默认 LTO 与 SELinux enforcing，Graviton 默认开 malloc 大页
计算 内核
AWS 公布 Amazon Linux 2027 公开预览。相较 2023 版，本次带来大量软件更新与面向 AWS 云负载的性能调优。关键改动：默认采用 Linux 7.1 内核、默认启用 SELinux enforcing 模式、引入新加速器驱动；包全部以 -O2 构建并开启 LTO（链接期优化），x86-64 包目标 x86-64-v3（假定 AVX/AVX2）、并启用自动向量化。
AArch64 Graviton 实例侧额外默认开启 malloc 堆 arena 的 透明大页（THP）。工具链默认 GCC 16.1 + LLVM/Clang 22，配套更新版 Rust / Go，包管理器换用 DNF5；系统部分基于 Fedora 44 / 45。基准测试将陆续放出。
关注理由：作为云上跑加速器/计算负载最常见的底层镜像之一，Amazon Linux 的默认基线直接决定「开箱性能」。本期信号是：x86-64-v3 + LTO + 自动向量化成为云镜像默认配置，意味着 SIMD 与跨模块优化不再需要用户手动重编——对跑 EPYC/加速器机群、以及依赖编译器自动向量化的计算后端是免费的收益。对团队评估「在 AWS 上部署 zeus/加速器软件栈的基线」，值得注意 SELinux enforcing 默认开启对驱动加载/设备访问权限的影响，以及 Graviton 侧 THP 对大内存分配型负载（模型权重、RDMA 缓冲区）的潜在提速。

GCC 17 合入 RISC-V 的 -mtune=native / -mcpu=native：原生代码生成与调优不再需记忆具体 CPU 名
计算
SiFive 的 Kito Cheng 把 RISC-V 的 -mtune=native / -mcpu=native 支持合入 GCC Git，将随 GCC 17.1（预计 2027 年初）发布。此前 GCC 在 RISC-V 上不支持这两个「native」选项，想要针对本机 CPU 做代码生成与调优，只能手动记住并填写形如 sifive-p550、spacemit-x100 等具体值。
合入后，在 RISC-V 系统上直接传 -mcpu=native 与 -mtune=native 即可。已知限制：对同时含多种核心类型的设计（如 SpacemiT A100/X100 组合），GCC 依据编译器进程最终落到的核心来选 CPU 类型。
关注理由：「native」调优是编译器对异构/多核平台最实用的能力之一——过去在 RISC-V 板卡上部署计算负载，要么手填 CPU 型号（易错、难移植），要么放弃针对性优化。GCC 17 补齐后，同一份构建在任意 RISC-V 目标上都能自动吃满本机微架构特性，对把计算后端（含 NPU/加速器软件）带到 RISC-V 客户端/边缘设备是前置利好。同时需留意其多核类型取舍限制：在大小核/异构 RISC-V 平台上，native 调优可能只覆盖编译器进程当时所在核心，这与团队在混合拓扑（如 zeus 的大小核/加速器组合）上的调优策略需要区别对待。
