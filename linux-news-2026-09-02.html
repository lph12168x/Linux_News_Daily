AMDGPU 驱动拆分出 HDMI Passive VRR 补丁：告别切 VRR 时的黑屏与亮度闪烁
显示
AMD 在持续推进 AMDGPU 上游内核图形驱动对 HDMI 2.1 的支持，今日把「Passive VRR（被动可变刷新率）」从原先的 HDMI 2.1「gaming」补丁系列（含 VRR 与 ALLM）中单独拆出为一个独立补丁系列（作者 Jerry Zuo，补丁见原文 lore 链接）。
Passive VRR 解决的问题是：当 HDMI 输出从固定刷新率切入 VRR 模式时，避免出现屏幕黑屏或亮度闪烁。DisplayPort 与 eDP 规范要求无缝 VRR 切换、本就无此问题，但 HDMI 没有——Passive VRR 的做法是让 HDMI sink 在固定刷新率的桌面使用期间也保持在可变刷新状态，从而平滑过渡。
该补丁在 AMDGPU 驱动中默认启用 Passive VRR，但也提供退出开关（若你偏好切换瞬间的黑屏/闪烁）。希望这批 HDMI 2.1 增补能在 10 月下旬的 Linux 7.4 合并窗口前完成评审与准备。
关注理由：VRR over HDMI 长期是 Linux 桌面在电视/显示器上体验的痛点，而「切 VRR 不黑屏」是 display/DRM 驱动里很能体现工程功力的细节。Passive VRR 的「让 sink 始终驻留 VRR 状态」是一套干净可复用的模式，对做显示/DRM 驱动的团队是直接参考。更宏观地看，这仍是 AMD 把 HDMI 2.1 全家桶（FRL / VRR / ALLM）逐块上游化 的一环——配合此前默认启用 FRL、VRR 等进展，Radeon 在 Linux 下的 HDMI 2.1 体验正从「能用」走向「完整」。

Intel Xe 驱动首发 Linux 7.4 特性 PR：引入冷复位恢复，Panther Lake 启用 IBC v3
图形
Linux 7.3 合并窗口刚于上周日收口，Intel 周一便向 DRM-Next 发出了面向 Linux 7.4 的首个 Xe 内核图形驱动特性 PR。本 PR 的几项重点：
· 冷复位恢复（Cold Reset Recovery）：引入 DRM_WEDGE_RECOVERY_COLD_RESET，用于那些 PCIe reset 或重载驱动都无法恢复、必须整机断电再上电才能解除的「持久硬件错误状态」。该机制与用户态协同完成 Intel 显卡的完整冷复位。
· Panther Lake Xe3 核显启用 IBC v3：Intelligent Bias Control v3 带来 Panther Lake 专属的功耗优化（源自新版 GuC 固件），有望在游戏及类似负载下改善 Panther Lake 核显的电源管理。
· 其他：新增 DRM_RAS Netlink 错误事件、VF 迁移、多队列并行页错误处理、DRM_RAS 错误阈值，以及 PCI 错误调试增强。
关注理由：GPU 挂死恢复是生产环境图形/计算可用性的命门。Intel 这套「wedge recovery」框架（与用户态协作的冷复位）是业界主流做法，对任何自研 GPU/加速器驱动都有架构参考价值——如何在不破坏用户态的前提下完成「硬复位」。而 IBC v3 把 Panther Lake 核显的游戏/轻量计算功耗进一步压低，是「固件算法（GuC）驱动能效」的典型范例。对跑 GPU 计算集群的团队，RAS Netlink 事件与错误阈值也是把显存/硬件错误接入监控体系的接口信号。

Zen 6 客户端 CPPC 改动：硬编码把低功耗核频率定为性能核的 0.47x
计算
继昨日为 Zen 6 客户端调校 ACPI EPP 的补丁后，又一组面向下一代 Ryzen Zen 6 客户端的 CPPC（Collaborative Processor Performance Control）补丁现身邮件列表。CPPC 是 ACPI 规范里 OS 与平台协作管理 CPU 核心频率与功耗缩放的接口。
Zen 6 客户端平台对 CPPC 的用法与既往世代不同：需要知道每种核心类型的最大频率才能做容量计算。未来 ACPI 规范修订会引入读取核心类型最大频率的新接口，在此之前，内核为 Zen 6 客户端硬编码了若干频率值：性能核 5025、效率（dense）核 3524、新增的低功耗核类型 2399 MHz。由此，低功耗核 ≈ 效率核的 0.68x、性能核的 0.47x。
同时，Zen 6 及更新的 boost ratio 改为由频率值推导，而非沿用任意的性能值标度。因错过 v7.3，这批补丁最早随 Linux 7.4 主线（可能挤进 12 月底的年度 LTS）合入。
关注理由：这条确认了 Zen 6 的三级核心拓扑（性能 / 效率 / 低功耗），而 0.47x 这个硬编码数字正是调度器做容量建模的关键输入。对做异构调度、NPU 伴生调度的团队有两点直接借鉴：其一，当 ACPI/硬件接口尚未就绪时，先用硬编码把新核心类型「解锁」给调度器，避免阻塞后续工作（这正是 AMD 的做法，也呼应了此前 EPP 补丁里「按 SoC + 按核心类型参数化」的框架）；其二，一旦标准接口到位就及时迁移，硬编码只是临时桥接。其背后教训是：新硬件的调度就绪度，往往卡在「固件/ACPI 还没把信息给全」这一环。

Steam 8 月调查：Linux 占比回落至 3.9%，CachyOS 在 Linux 玩家中升至 15.4%
图形
Valve 发布 2026 年 8 月 Steam 硬件调查。继 7 月占比一度冲上 4% 以上后，8 月回落至 3.9%（较 7 月微降 0.11 个百分点）；今年 3 月曾创 5.33% 的纪录高点，此后在 3%~4% 区间波动。绝对值上 Linux 玩家规模可能并未缩水，只是缺乏 Steam 总量的新鲜数据难以精确评估。
发行版分布：SteamOS 以 21% 领跑 Linux 发行版（即 Steam Deck / Steam Machine 的 Arch 衍生系统）；CachyOS 以 15.4% 位居第二，环比 +1.16%。CPU 侧，Linux 玩家中 AMD CPU 占比仍在上六成（Steam Deck / Steam Machine 的定制 AMD SoC + 整体开源友好度驱动），而 Windows 侧 AMD CPU 占比已升至 45%。
关注理由：Steam Deck / SteamOS 是拉动 Linux 开源图形栈投资的最大单一引擎——Valve 对 RADV、Mesa、DXVK/VKD3D 的持续投入都源于此。跟踪 Linux 游戏占比，本质上是在看你所在图形生态的动量：占比越高，上游（Mesa / RADV / 游戏兼容层）获得的资源与回归测试就越多，最终惠及所有 Linux 图形工作。CachyOS 的崛起也值得留意：这个以性能为卖点的 Arch 衍生版在玩家群体里的扩张，可能成为「极致调校」需求的新风向标。

Linux 7.3 合并 EDAC 改动（曾遗忘于合并窗口）：AMD 仅在 ECC 平台加载 ATL，Intel Starfire 入列
计算
Linux 7.3 合并窗口已于上周日随 7.3-rc1 正式收口，但 EDAC（Error Detection And Correction，错误检测与纠正）子系统的改动在两周窗口期内被意外遗忘；该 PR 直到周一晚间才发出，Linus Torvalds 同意后将这批迟到特性合入 Git。
· Intel 侧：iGEN6 EDAC 驱动合并 Starfire SoC 支持——Starfire 是面向太空等极端环境的 Panther Lake 衍生型号；iGEN6 与 iE31200 客户端 EDAC 驱动还统一了部分地址转换逻辑。
· AMD 侧：地址转换库 ATL 现在只在真正具备 ECC 内存的系统上加载。此前 ATL 会在所有 AMD Zen 系统上加载，非 ECC 平台便会因加载失败而在内核日志里刷屏；现在仅在 Zen ECC 平台上加载，规避该问题。
· 其他：ThunderX（原 Cavium/Marvell ARM SoC）与 MPC85XX（Freescale/NXP PowerPC）EDAC 驱动因无人维护被标记为 orphan，未来可能移除。
关注理由：对运行 GPU/加速器机群的团队，内存错误上报（EDAC）是 RAS 的基石。AMD 这处「仅在 ECC 平台加载 ATL」是个教科书级的驱动初始化门控优化——避免在非目标硬件上产生噪声日志与潜在初始化失败，值得任何带可选硬件模块的内核/固件栈借鉴。而「合并窗口被遗忘、Linus 网开一面」的小插曲，也提醒我们：迟到特性能否进主线有时取决于维护者的好脾气，关键补丁务必在窗口期内跟紧。Starfire 入列则显示 Intel 把服务器级 RAS 能力向更严苛环境延伸。
