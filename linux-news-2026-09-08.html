Nouveau 准备 HDMI 2.1 DSC、AMD 修复 FreeSync：面向 Linux 7.4 的 DRM-Misc-Next 显示改动
显示 图形
上周合入 DRM-Next、面向 Linux 7.4 的 DRM-Misc-Next 拉取带来 AMDGPU 与开源 Nouveau（NVIDIA）驱动的 HDMI 2.1 相关改动。Nouveau 部分支持 Blackwell GPU 的 2.147GHz 像素时钟，为 HDMI 2.1 DSC（显示流压缩）铺路——目前非压缩 HDMI FRL 仅约 1.78GHz，DSC 接好后才够到更高上限；此外终于默认启用 Nouveau 原子模式设置（atomic mode-setting），追平其它 DRM 驱动。AMDGPU 侧修复了 DRM EDID 解析器对 AMD VSDB FreeSync 的处理，使部分只在 AMD 厂商数据块声明 VRR 的显示器能被正确识别。
关注理由：对做显示栈的团队，这是「高带宽显示特性要先把链路底层约束修好」的又一次印证：Blackwell 的 2.147GHz 像素时钟上限与原子模式设置是 HDMI 2.1 DSC / VRR 的前置地基，与我们在 zeus 上「先稳显示链路、再上高刷新 / 压缩」的顺序一致；AMD FreeSync 的 EDID/VSDB 解析修复则说明「显示器能力探测」这类看似边角的解析逻辑，常决定 VRR 能否真正启用——做显示兼容清单时要把 EDID/VSDB 的 VRR 声明方式纳入。

Asahi Linux 正式支持 Apple M3 Mac：GPU 仍非性能 / 功耗可用、HDMI 因缺 DCP 不可用
图形 显示
Asahi Linux 开发者宣布 Apple M3 系列 Mac（M3 / M3 Pro / M3 Max，除 Mac Studio M3 Ultra 外）已达到「几乎所有」功能可用的正式支持状态，接近早先 M1/M2 的成熟度。最大例外是 GPU 支持——目前 3D 加速在性能与功耗上都还不够好，团队期望未来数月有进展。此外 M3 上暂无睡眠支持（缺 DCP 支持），且无 DCP 导致 M3 MacBook 的 HDMI 口也不可用。主线内核已有 M3 基础启动支持，其余补丁仍在向 Linux 7.4+ 上游化。
关注理由：对做 GPU/显示移植的团队，M3 的「GPU 仍非性能/功耗可用 + HDMI 因缺 DCP 不可用」是典型 bring-up 中期状态——可对照我们新加速器平台「先点亮、后加速、显示外设最后补」的节奏；且 Asahi 把「基础启动先进主线、图形/显示/DCP 等后续补丁分批上游」的拆分策略，正是评估新 SoC 移植成本与风险时的范本：先拿到能 boot 的最小集合，再按 GPU → 显示 → 功耗的顺序解锁。

Shotcut 26.9 视频编辑器 Beta：音频全程 32-bit float、FFmpeg 9.0 修复 VA-API HEVC 硬编
显示 计算
开源视频编辑器 Shotcut 26.9 Beta 发布，带来多项改进：音频管线全程保持 32-bit float、避免 16-bit 整数转换以提升音质；时间线性能改善；UI 现代化（圆角等细节）并启用新 logo。底层升级到 FFmpeg 9.0，修复了 Linux 上的 VA-API HEVC 硬件编码，并提供 Linux AppImage、macOS、Windows 多平台构建。
关注理由：对做多媒体/显示栈的团队，Shotcut 26.9 两点值得记：其一，音频管线「全程 32-bit float 不降级」是 DAW/编辑器常见的音质做法，可对照我们合成器/采集链路的位深策略；其二，FFmpeg 9.0 + VA-API HEVC 硬件编码修复说明 Linux 上的硬编（尤其是 HEVC）正在持续被修好，做视频采集/串流/录屏方案时应优先验证 VA-API HEVC 路径是否已被当前 FFmpeg 修复覆盖。

Linux 准备 AMD Zen 6 BTB 上下文隔离：硬件级分隔 user/kernel 与 guest/host
计算 内核
新近发布的 Linux 内核补丁揭示了 Zen 6 的一项安全改进：在受 SRSO 漏洞影响的 Zen 1~4 之后，Zen 6 引入分支目标缓冲（BTB）保护，隔离不同上下文（user/kernel、guest/host）之间。AMD 工程师说明，BTB 隔离使该平台上的 SafeRET 缓解不再必要，仅剩下 user/user 与 guest/guest 攻击面由 Spectre v2 的 IBPB 上下文切换缓解覆盖。补丁已进入 tip/tip.git 的 x86/bugs 分支，预计随 Linux 7.4 合入（或作为 7.3 的修复）。
关注理由：对做计算/虚拟化安全栈的团队，Zen 6 的 BTB 上下文隔离意味着「CPU 微架构级把 guest/host、user/kernel 的 BTB 隔离开」，可减少一类跨上下文推测侧信道——这与我们评估加速器上多租户/虚拟化隔离时的硬件信任边界直接相关；同时提示：新的硬件隔离特性会逐步改写下层缓解（如 SafeRET 可被替代），做安全基线时要跟踪 CPU 代次对应的缓解组合变化。

Linux 7.3-rc2 修复混合 CPU 缓存感知调度 misfit：局部性与算力容量要同时校验
计算 内核
在 Linux 7.3-rc2 之前的调度器修复中，重点是修复混合 CPU（如 Intel Core Ultra 大小核）上「缓存感知负载调度（Cache-Aware Load Scheduling）」的 misfit 问题。Cache-Aware Scheduling 把共享末级缓存（LLC）的任务聚到一起以提升缓存局部性，但在 big.LITTLE 混合架构上，分组任务可能被全部压到小核而成为 misfit。Intel 工程师 Tim Chen 的修复在两个入口加护栏：can_migrate_llc_task() 禁止「源 CPU 能容纳、目的 CPU 装不下」的 LLC 迁移；alb_break_llc() 在相同条件下否决主动均衡；两者仅对混合处理器生效，对称系统不受影响；并在负载均衡阶段优先处理 misfit 任务迁移。
关注理由：对做异构计算/调度栈的团队，这条修复是「缓存局部性 vs 算力容量」权衡的教科书案例——在 big.LITTLE（或我们加速器上的异构计算簇）上，单纯按 LLC 亲和把任务聚拢，可能把重负载误推到小核而更伤性能。可借鉴点：其一，亲和/局部性策略必须同时校验「目的算力是否装得下」，否则收益为负；其二，护栏只对混合系统生效、对称系统无感，提示我们在设计调度策略时应按拓扑差异做条件化，避免对对称平台施加无谓开销。
