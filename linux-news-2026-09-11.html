Mesa 26.3：RADV + RadeonSI 补齐老 AMD GPU（GCN1.0~Polaris）的 DRM 格式修饰符支持
图形
Valve 的 Timur Kristóf 把 AMDGPU GFX6~GFX8（Radeon HD 7000 初代 GCN1.0 一直到 Polaris / Fiji）的 DRM 格式修饰符（format modifiers）合入了当前 Linux 7.3 周期（10 月转 stable），如今对应的用户态一侧（RadeonSI + RADV）也已合入 Mesa 26.3（11 月转 stable，可能回移植到 26.2）。修饰符描述了图像缓冲的 tile / 压缩 / 布局等属性，让这些老卡得以支持基于 Vulkan 的 Wayland 合成器、更好的 OpenGL↔Vulkan 互操作，以及跑在 Zink（OpenGL-on-Vulkan）之上的合成器。GFX9 及更新架构此前已支持。
关注理由：对做图形栈的团队，这是「DRM 格式修饰符下沉到老硬件」的补全：它本质是贯通 GPU 厂商布局（tiling/compression）与合成器/跨 API 共享的握手协议。我们 zeus 显示/计算路径若要做多后端 buffer 共享、或让计算产出直接喂给 Wayland 合成器，格式修饰符就是绕不开的互操作原语；而 Valve 亲自推动老卡兼容 Vulkan Wayland，也印证「老硬件 + 新合成栈」是 Linux 桌面的长期主线，值得跟进其 Mesa 侧实现方式。

NVIDIA NVK 开源驱动落地一项改进，帮 Valve Gamescope 微合成器提速录制与远程游玩
图形
Mary Guillemard 为开源 NVIDIA Vulkan 驱动 NVK 合入一处改动：把 BAR 显存类型暴露为 host cached。改动说明：Nouveau 默认只用 CPU cached 映射（Tegra 需一致性时除外），本补丁让 BAR 内存类型声明为 host cached——Gamescope 会显式寻找「host visible + cached」的内存类型，此前缺这项声明会迫使其对所有可映射分配都选 sysmem。作者称这「至少应能改善游戏录制与远程游玩（remote play）的性能」，已合入 Mesa 26.3，或将回移植到 26.2 stable。
关注理由：对做图形/显示后端的团队，这条很小但很「教科书」：一个 host cached 内存类型声明的缺失，就让 Gamescope 退化为全 sysmem 分配，直接拖慢录制/串流。它提醒我们：在 zeus 上若要让合成器/串流走显存而非系统内存，内存类型（host visible/cached/coherent）的暴露必须和上层消费者（Gamescope、串流、录制）的预期逐一对齐，否则会静默退化。这类「声明正确但被忽略」的坑，正是 bring-up 期最该提前对照的点。

X.Org Server 26.1 RC2 发布：自 21.1 以来首个特性版，五年磨一剑逼近稳定
显示
X.Org Server 26.1 将是自 2021 年 10 月 X.Org Server 21.1 以来首个新的带版本特性发布，堪称「半代际」更新。本周推出的 RC2（上月已出 RC1）带来 XKB、X Input 等修复与 Meson 构建系统更新，并抬高了 X.Org Server 的扩展版本与视频驱动 ABI——这对 NVIDIA 打包驱动等依赖特定 ABI 版本的各方很关键。稳定版发布在即。
关注理由：对做显示/驱动的团队，X.Org Server 26.1 的 ABI 抬高是必须盯的兼容信号：NVIDIA 闭源驱动、各厂商 DDX 都按 ABI 版本对齐，ABI 一变就要重新适配。它和 XWayland 26.1 的推进一起，勾勒出「X 服务端本体与 XWayland 兼容层同步现代化」的节奏；在 zeus 显示栈上我们要决策「X 兼容层维护到什么程度」，这类发布节点就是评估窗口。

KDE Plasma 6.8 Beta 发布：vRAM 优化 + KWin 接入 Wayland 提交时序协议 + 多 GPU/多屏增强
显示
KDE Plasma 6.8 Beta 已出（稳定版定于 10 月 14 日，恰逢 KDE 项目 30 周年）。亮点含：vRAM 占用优化、Wayland 下 dwell clicker 支持、KWin 接入 Wayland commit-timing 协议、Union 主题引擎改进、远程桌面增强、多 GPU 处理改进、新 kscreenctl 工具、服务端投影（drop shadow）支持、多显示器改进等，并首次把 Kup 作为桌面备份调度器。Wayland 方向打磨尤其密集。
关注理由：对做显示/合成的团队，Plasma 6.8 几乎是「现代显示痛点清单」：vRAM 优化（显存敏感场景）、commit-timing 协议（视频播放/自适应同步时序可控）、多 GPU 与多屏——每一项都和我们在 zeus 上要处理的呈现时序、多屏、多设备拓扑直接对应。KWin 率先吃下 commit-timing 也与 09-09 期 KDE 合入该协议一脉相承，说明 「合成器侧可预测呈现时序」已成主流桌面共识，我们的呈现栈设计应与之对齐而非另起炉灶。

近 400 项基准对决：Intel Xeon 600 工作站 vs. AMD Threadripper 9000（Linux）
计算
Phoronix 发布大型工作站对比评测，在 Linux 下以 近 400 项基准对 Intel Xeon 600（含新一代平台）与 AMD Threadripper 9000 两大工作站平台做了系统较量，覆盖编译、渲染、编码、HPC 等多类负载，并给出两家的定位差异与适用场景。（注：原文正文因抓取限制未能逐句核对，以下结论来自文章标题与公开摘要。）
关注理由：对做计算/工作站的团队，这类「近 400 项基准的 Xeon 600 vs Threadripper 9000」是选型最直接的参考：它把「多核吞吐、内存带宽、PCIe 拓扑、单核延迟」在多负载下的真实取舍摆出来。我们部署 zeus 类加速器时，主机 CPU 平台（核心数/内存通道/PCIe lane 数）往往决定加速器能否喂饱——这类对比能帮我们提前判断「计算密集 vs 延迟敏感」负载该选哪条主机路线，也提示 Linux 上的多厂商 CPU 工作站生态已相当成熟。

GIMP 3.2.6 发布：启动加载提速，并启动通往 GTK4 的早期准备
图形
GIMP 3.2.6 发布，作为去年才从 GTK2 迁移到 GTK3 的 3.0 之后的一次维护性更新，已开始为最终迁移到 GTK4做早期准备（清理废弃 API、使代码更「GTK4 友好」；GTK3→GTK4 比 GTK2→GTK3 侵入性小，但距「GIMP 4.0」仍有时日）。性能上大幅改善了加载大量字体时的卡顿；新增对图层组执行 Cut、绘画用的「Rotation（桶形旋转）」动态输入（适配新 Wacom 笔）；并补齐 macOS 与 Linux/Windows 同步打包、若干安全修复。
关注理由：对做图形软件/桌面的团队，GIMP 的节奏有两点可借鉴：① 「先清废弃 API、再迁 GTK4」的渐进路线比一次性大改更稳，我们若要做 UI 框架升级（如工具链/控件库换代）同样适用；② 它专门优化了「大量字体加载性能」——这类「资源密集初始化」瓶颈在带皮肤/字体的专业图形应用里很常见，提醒我们在 zeus 配套工具上也要对初始化路径做性能审计，而非只看渲染期。
