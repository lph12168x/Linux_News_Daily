AMD 在 LLVM 中新增「GFX1250-STRICT」GPU 目标，指向 Instinct MI450 加速卡
GPU 计算
GFX1250 IP 是 AMD 新一代 Instinct MI450 系列加速器所用的图形/计算 IP，过去一年已陆续进入 Linux 内核、AMDGPU LLVM 后端及相关代码库。昨日（8/25）已合并进 LLVM 代码库的是一个全新的 「gfx1250-strict」 目标：根据初始补丁，它在 ISA 能力上与 vanilla 的 GFX1250 完全一致，并复制了现有 GFX1250 定义；目前在 LLVM 中仅有这个 「12.5.0s」 的 strict 目标，GFX1251 版本并无类似定义。这是 Michael Larabel 在监测中首次见到 AMD GPU 出现「strict」IP 目标。其用途目前尚不明朗——可能是面向安全关键/加固环境的加速器，也可能是为现有 MI450 在受监管、需严格一致性的工作负载下提供的替代编译目标。相关 PR 为 llvm/llvm-project#218543。
关注理由：LLVM 编译后端是 ROCm/AMD 计算生态的基座，新增 GPU 目标意味着新一代 Instinct 加速卡的软件栈继续向前推进。虽然「strict」语义尚未公开，但它直觉上指向功能安全（FuSa）或严格一致性场景——这是 AI/HPC 加速器进入汽车、工业、医疗等受监管领域的必备能力。对从事 AMD GPU 计算与 ROCm 工具链的人，这是一个值得跟踪的早期信号。

Asahi Linux 有望很快发布带 Apple M3 设备支持的版本
显示 GPU
Asahi Linux 团队今日发布状态更新，主要围绕 Apple M3 bring-up 以及 M4/M5 的进展。主线内核电源管理方面：因上游要求 ARM64 设备使用 PSCI，而现有 Apple Silicon/Asahi 驱动设计与之不兼容，目前只有下游 Asahi 代码提供「deep」WFI；团队正实现基于 UEFI Runtime Service 的 PSCI conduit 以适配。M3 设备支持细节：麦克风处理微调、摄像头在 M3 上已可工作（新补丁）、最新下游代码已让 USB 3.0 与 Thunderbolt 可用。团队已接近发布带 M3 支持（基于下游代码）的版本；M4/M5 的 bring-up 仍在进行但工作量很大。此外 GPU direct scan-out（直扫）支持也在推进，但还需更多工作才能交付用户。详情见 AsahiLinux 博客。
关注理由：Asahi Linux 是把 Linux 图形栈（含 GPU 驱动、显示直扫）带到 Apple Silicon 的关键项目。M3 设备支持接近可用、GPU direct scan-out 正在推进，意味着 Apple 硬件在 Linux 下的显示体验正从「能启动」走向「体验可用」。对关注 ARM 平台图形/显示、以及想在 Mac 上跑 Linux 桌面/ Wayland 的用户，这是阶段性利好；摄像头、USB、Thunderbolt 的齐活也补上了 M 系列作为日常机的最后短板。

AMD 提出 LLVM iTHP 选项 -fenable-readonly-thp，进一步压榨性能
计算
AMD 编译器团队提出新的 Clang 选项 -fenable-readonly-thp，在编译/链接期实现 iTHP（指令透明大页）：驱动在链接期安排 2 MiB（或更大）段对齐，链接一个小型启动对象，并在进程启动时对可执行文本段调用 madvise(MADV_COLLAPSE)，让内核把默认的 4 KiB 页映射提升为巨页。其解决的问题是 iTLB 压力——大二进制 .text 因 4 KiB 映射而 frontend-bound。收益工作负载包括 SPEC CPU 2026、Geekbench、CPython、数据库/服务器，以及解释器、模拟器、编译器类二进制；代价是二进制体积变大与少量启动开销，且需 Linux 7.2+。相较 BOLT 它无需性能剖析；Google 工程师回应称已有类似库，AMD希望将其推进上游 LLVM（及可能的 GNU）工具链。
关注理由：iTLB 是 CPU 前端长期被忽视的性能瓶颈，对解释器、模拟器、大型服务端二进制尤为明显。AMD 把「2 MiB 段对齐 + 启动期 MADV_COLLAPSE」做成编译器托管的 opt-in 选项，比手写链接脚本/启动代码更易落地，是「免费」性能提升的工程化范例。对 Linux 上跑大型 C++/服务程序的团队，这是值得在构建链验证的编译器特性；也体现 AMD 在 LLVM 工具链上的持续投入。

Intel Granite Rapids 工作站核心扩展评测：Xeon 678X 6→48 核性能/功耗/频率全扫描
计算
在归还 HP Z4 G6i 评测机前，Phoronix 对 Xeon 678X「Granite Rapids WS」 做了核心扩展（core scaling）评测。该处理器为 48 核 / 96 线程，基础频率 2.4 GHz、Turbo Boost 2.0 4.7 GHz、最大单核睿频 4.9 GHz，TDP 300 W，采用 Redwood Cove 性能核。测试平台：4×32GB DDR5-6400、2TB NVMe，运行 Fedora 44 + Linux 7.1 内核 + GCC 16.1。评测分别限制为 6 / 12 / 24 / 48 核 以及 48 核 + 超线程，并同步监控峰值 CPU 频率、通过 RAPL/PowerCap 暴露的功耗、核心温度，最终给出每瓦性能表现，直观呈现该高端工作站处理器的扩展特性。
关注理由：核心扩展曲线是判断「买多少核划算」的硬数据——对选型、虚拟化切分、HPC/编译农场部署都有直接参考价值。Granite Rapids WS 作为 Intel 在高端桌面/工作站对抗 AMD Threadripper/EPYC 的旗舰，其在 Linux 下的每瓦性能与频率/热墙行为是 Linux 计算用户的决策依据。结合此前同平台的超线程开关评测，这份 6→48 核全扫描补齐了 Granite Rapids 在 Linux 上的性能画像。

内核 Zstd 补丁大幅提速：修复「离谱的低效」，解压时间降 71%
内核
今日发往 Linux 内核邮件列表的补丁，通过修正一处「非常不幸的疏忽」让内核 Zstd 压缩/解压更高效。现有 in-kernel Zstd 在每次创建上下文时，都会运行时探测是否走 BMI2 指令路径（BMI2 见于 Intel Haswell+ / AMD Excavator+，即过去十年的大多数 CPU）。问题在于：探测用两条串行化 CPUID 指令 + 无条件 VM exit，且发生在极热路径——SquashFS 每解压一个 block、EROFS/Btrfs/F2FS 每操作、crypto/zstd 每操作都会触发。修复方案是把 BMI2 探测只做一次，在 crypto_acomp 基准上带来解压时间减少 71%、压缩时间减少 18%。补丁已在 LKML 评审中。
关注理由：这是「一行冗余变成热点」的典型内核性能故事——一个本应只做一次的能力探测，被放在了每操作必走的路径上，长期拖累所有使用内核 Zstd 的文件系统与压缩栈。对用 SquashFS/EROFS/Btrfs 做镜像、容器层、存储的用户，该补丁直接降低 CPU 开销与延迟；也再次提醒：看似无害的运行时探测，在热路径上就是性能雷。
