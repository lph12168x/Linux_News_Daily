AMD 在 Linux 7.3 合并窗口前塞入最后一轮图形驱动更新
GPU 内核
AMD 于 8 月 6 日提交了 Linux 7.3 合并窗口（预计 8 月下半月开启）前的最后一批计划内功能更新，拉取代号 amd-drm-next-7.3-2026-08-06、由 Alex Deucher 发出。此前数周 AMDGPU/AMDKFD 已陆续带来老硬件 GPU 复位恢复、老硬件 DRM 格式修饰符（Valve 赞助）、GFX11 APU 第二图形管道等改动，本轮则做收尾：更新 SMU 15 IP 与 SMU 14/PPT、重构 Display Core（DC）流验证（stream validation）、修复经典 Radeon DRM 驱动的性能回退、借助 Valve 的 Timur Kristóf 重做老 GFX6 图形 IP 的软复位（改善早期 GCN 卡的软复位恢复），并加入一系列修复。具体清单中值得图形/显示方向留意的包括：DCN 6.0.0 初步支持（即指向 RDNA5/GFX13 的显示引擎首次进入主线路径）、FRL / VRR 修复、更多显示 KUnit 单元测试、DC avmute/self refresh/CRC 修复、DCN 2.0.1/3.2/3.5.1 修复；AMDKFD 侧则是 SVM 与 MES 更新；老的 radeon 驱动也获得一处性能回退修复。
关注理由：这是 7.3 周期 AMD 图形栈的「关门补丁」，几乎集齐了本周期 AMD 在 GPU 复位、显示（FRL/VRR/DCN6）、老硬件维护上的全部收尾工作。DCN 6.0.0 的首次出现尤其值得注意的是：它把 RDNA5 的显示引擎正式铺到了上游主干路上，是未来一年 AMD 新卡的显示能力地基。

AMD GFX1171 支持合入 Mesa 26.3（RDNA 4m 家族再添新成员）
GPU
继今年早些时候 AMD 以「RDNA 4m」为名先后加入 GFX1170、GFX1171、GFX1172 三个 AMDGPU LLVM 编译器后端与内核驱动目标后，Mesa 侧今天合入了 GFX1171 目标，供 RADV（Vulkan）与 RadeonSI（OpenGL） 驱动使用。这一合并（MR !43094）本质上只是新增芯片 ID，其余代码路径沿用 GFX1170，而 GFX1170 大体又沿 GFX115x / RDNA 3.5 的路径——属于相对直白的例行添加。GFX1170 的支持早在 4 月即合入 RADV/RadeonSI，但 GFX1171 拖到今天才进 Mesa，GFX1172 则尚无 Mesa 目标，提示这些额外的 RDNA 4m 变体预计要晚于首发型号数月才陆续面世。
关注理由：GFX1171 的合入意味着 Mesa 26.3（预计 Q4 发布）将能识别并驱动又一款 RDNA 4m 衍生 GPU。对 Linux 图形栈而言，这延续了「AMD 新硬件上游化节奏越来越快」的趋势——尽管只是 ID 层面的小步，却是用户拿到新卡即开箱可用的前提。

实测：Intel Arc B390（Xe3）升级 Mesa 能带来可观性能提升
GPU 计算
Phoronix 在 Framework Laptop 13 Pro（Intel Core Ultra X9 388H、64GB LPDDR5-7467、Arc B390 Xe3 核显）上做了对比：默认 Ubuntu 26.04 LTS 自带的 Mesa 26.0 与通过 Mesa ACO PPA 升级到 Mesa 26.3 Git（7 月 31 日快照）之间的性能差异。结论是：Panther Lake 的 Arc B390 图形本身不错，但用 Ubuntu 26.04 默认 Mesa 26.0（或当前仍用 Mesa 26.0 的 26.10 每日构建）会白白丢掉不少优化——新 Iris Gallium3D 与 ANV Vulkan 驱动在 26.3 上积累的性能改进相当实在。Ubuntu 用户借助 Mesa ACO PPA 即可轻松把 Mesa 升到最新 Git 以复现测试。
关注理由：这是「发行版默认 Mesa 偏旧」在最新平台上直接变现为性能损失的鲜活例证。早期 Panther Lake 笔记本用户只要换一套更新的 Mesa，就能免费获得 Iris/ANV 的近期优化；同时也再次提醒：Linux 图形体验有一半取决于发行版打包的 Mesa 版本。

IceWM 4.1 窗口管理器发布：修复罕见视频性能问题
显示
老牌 X11 窗口管理器 IceWM 自今年元旦 4.0 之后迎来首个新版本 4.1。本版以一堆 bug 修复为主，最值得注意的是修复了罕见的视频性能问题——具体做法是把默认的 Alpha 合成开关设为 false，以避免某些场景下视频播放性能劣化；同时还修复了配置文件未终止字符串的处理、_NET_STARTUP_ID 字符串解析错误、以及「先释放 picture 再释放其 pixmap」导致的报错。功能侧新增了 ignoreUserTime 窗口选项（issue #833）与 icesh 的 mousemove 命令，并附带翻译更新。
关注理由：IceWM 体量小、在轻量/嵌入式/老旧硬件桌面上仍有用户，把默认 Alpha 合成关掉以规避视频性能回退是个务实的兼容性修复；它也侧面说明「合成器 Alpha 混合」这类看似无害的默认项，在特定视频路径上仍可能踩坑。

高通提议把 Synx 全局同步框架上游进 Linux 内核
计算 内核
高通工程师在邮件列表发起 RFC，讨论将 Synx 上游进 Linux 内核。Synx 是一个跨越 SoC 内不同部分的全局同步框架，用于在 Linux 托管的客户端与非 Linux 执行环境（远程处理器、固件）之间协调 fence。高通已在内部使用，并宣称带来「显著」的功耗与性能收益。其定位并非取代图形/显示领域现有的 dma-fence，而是作为横跨多个子系统与处理器的全局同步机制，同时在合适处与 dma-fence、sync_file 等现有 Linux 原语集成；该框架被设计为厂商无关（SoC-agnostic），未来其他厂商也可采用。据 RFC 说明，Synx 在近几代高通移动与 XR 芯片上已展现显著的功耗/性能收益，且用例仍在扩展。
关注理由：图形与显示同步（dma-fence）是把控 GPU/显示流水线正确性的关键原语，Synx 把它从单子系统扩到整个 SoC 跨核/跨固件层面，对异构计算与 XR 这类「多处理器协同渲染」场景意义重大；而「厂商无关」的设计定位，决定了它能否真正进入主线、成为通用的异构同步基础设施。

Page Alloc Hogger：Google 提议的 Linux 内存压力测试特性
计算 内核
Google 工程师 Juan Yescas 提出名为 Page Alloc Hogger 的新内核特性，用于精细控制内存页的分配位置，从而更轻松地复现低内存条件、施加内存压力并触发各种压力场景以便测试/调试 Linux 的内存行为。它经 DebugFS 暴露接口，允许开发者从指定节点（node）、区间（zone）、迁移类型与阶（order）分配内存页。其用途包括：复现直接回收、kswapd、OOM killer 与分配回退等内核机制；免写自定义内核驱动或用户态分配程序即可调试仅在内存压力下才暴露的问题；在测试套件中验证内存管理子系统按预期触发；以及衡量应用在严重内存压力下的行为表现。该特性严格面向测试/调试，不面向终端用户。
关注理由：内存管理是内核正确性与性能的地基，Page Alloc Hogger 把「可控地制造内存压力」做成内核内一等公民，能大幅降低复现 OOM/回收类难题的门槛。对跑大模型、NPU 推理等内存敏感负载的 Linux 平台而言，这类可观测/可压测工具越成熟，稳定性调优越省力。
