GNOME 51 正式发布：Mutter 帧调度改进提升响应性，移除旧版 NVIDIA EGLStreams 支持
显示 图形
GNOME 51 如期正式发布，正好赶在 Ubuntu 26.10 与 Fedora Workstation 45 的采纳窗口之前。本次最核心的是 Mutter 的一组改进：通过更好的帧调度（frame scheduling）提升桌面响应性与整体流畅度，并新增若干 Wayland 协议支持（例如 ext-background-effect-v1），同时移除了对旧版 NVIDIA 驱动的 EGLStreams 支持。Mutter 还开始支持自定义指针加速曲线（custom pointer acceleration profiles）。应用层也有一批更新：设置项改进、GNOME Maps 支持离线地图、GNOME Software 启动更快、GNOME Calendar 更快，以及 GNOME File Previewer 界面全面重做。完整变更见官方发布说明 release.gnome.org/51/。
关注理由：对做显示/合成栈的团队，GNOME 51 的三个动作值得单独记下：① 帧调度成为桌面合成器的核心竞争点——Mutter 这轮改进与 GTK 4.24 的 GDK frame-clock 重做、KDE KWin 合入 commit-timing 是同一波趋势，说明「谁能把帧的提交时机交给应用并精确控制」正在决定桌面流畅度上限；② 彻底移除 EGLStreams 标志着一个历史兼容分支正式谢幕，也提醒我们旧路径的清理通常滞后硬件支持数年，维护自有显示栈时需显式规划弃用节点；③ 帧调度 + 背景模糊协议 + 指针曲线都属于「时序与感知质量」类优化，成本低、收益直接，是 zeus 侧显示方案中优先级很高的投入方向。

Mesa 26.2.3 发布：回移 AMD GFX1171（RDNA 4m）目标，RADV/RadeonSI/ANV/NVK 齐修
图形 内核
Mesa 26.2.3 发布，是 26.2 系列最新的稳定点版本。这个由 Eric Engestrom 维护的双周节奏点版本，把当前 Mesa 26.3 开发代码中的大量修复回移：AMD GPU 方面有多个 RadeonSI 与 RADV 修复；Qualcomm Adreno 方面有 Freedreno 与 Turnip 修复；Intel ANV 修复中包含针对 X-Plane 12 飞行模拟器的 workaround；Asahi Gallium3D 把原先只对 Firefox 生效的 workaround 扩展到 Zen 浏览器，以解决撕裂与渲染问题；NVK 修复了内存泄漏。此外 AMD GFX1171 目标也被回移到 26.2.3——它上月才进 Mesa 26.3，属于 GFX117x 系列中的又一个 「RDNA 4m」变体，特点是并非完整的 GFX12/RDNA4 实现，目前公开信息仍然有限。
关注理由：对做 GPU 驱动/图形栈的团队，这条有两个可操作信号：① 「RDNA 4m」这类降级/裁剪变体正在稳定地进入 Mesa 主线与稳定回移通道，意味着 AMD 在消费级之外的衍生 SKU 会持续以既有驱动栈为基础小步适配，而不是另立驱动分支——我们做自有加速器命名与驱动分层时，可参考这种「同一后端 + 细粒度目标开关」的收敛策略，避免为每个 SKU 分裂代码路径；② 点版本把游戏 workaround 与内存泄漏修复作为主要回移内容，说明驱动栈的稳定性成本大头在「应用兼容 + 资源生命周期」而非新特性，zeus 侧的驱动验收清单应把这两类列为常规回归项。

Miracle-WM 0.11 发布：新增「华丽的」overview 模式，吃下整批 ext_ 协议
显示
Canonical 工程师 Matthew Kosarek 发布了 Miracle-WM 0.11，这是构建在 Mir 库之上的 Wayland 合成器的夏末更新。本次主推特性是全新的 overview 模式，作者形容其「非常华丽」，目的是帮助在多个窗口与工作区之间快速选取，可通过单击或双击主操作键呼出。0.11 还新增了窗口 urgency 支持（某个窗口或非当前工作区请求聚焦时给出提示），并让插件支持发布 IPC 事件与处理 IPC 命令。合成器同时用上了 Mir 更新版的协议支持，包括 ext_image_copy_capture_manager_v1、ext_output_image_capture_source_manager_v1、ext_foreign_toplevel_list_v1、ext_data_control_manager_v1、ext_input_trigger_action_manager_v1 与 ext_input_trigger_registration_manager_v1。该版本基于 Mir 2.29 构建。
关注理由：对做显示/合成栈的团队，Miracle-WM 的价值不在知名度，而在它是一个由单个厂商工程师维护、把新协议快速落地的「先行样本」：ext_image_copy_capture 系列（屏幕捕获）、ext_foreign_toplevel_list（跨合成器窗口列表）、ext_data_control（剪贴板管理）都是目前桌面体验短板所在，抢先把它们做通的项目会暴露真实的协议边界与性能问题。另外 overview 模式这类全屏合成效果对 GPU 有明确要求（多窗口实时缩放合成），正是能压出驱动瓶颈的负载类型，值得作为我们验证显示/合成路径的参考场景；而「插件 + IPC 事件/命令」的扩展模型也比编译期插件更利于生态生长，可作为 zeus 侧显示扩展机制的设计参考。

Ubuntu 26.10 amd64v3 对低端笔电同样有效：$449 Wildcat Lake 机型实测（1P+4LPE / 8GB）
计算 内核
Canonical 近期开始产出 Ubuntu 26.10 的 amd64v3 每日 ISO，配套其已试运行数个版本周期的试验性 amd64v3 软件包仓库，不过官方是否在 26.10 正式采用仍未公布。amd64v3 / x86_64-v3 构建可以假定 CPU 具备 AVX/AVX2、BMI2、MOVBE、FMA 等较新的 ISA 能力——这些能力在 Intel Haswell 之后或 AMD Excavator 之后的 CPU 上已经具备。此前 Phoronix 的 amd64v3 基准多在高性能硬件上进行，本次刻意下沉到入门级：使用 $449 的 CHUWI UniBook（Intel Wildcat Lake 平台、Core 3 304、1 个 P 核 + 4 个 LPE 核、8GB 内存），先在纯 amd64 每日构建上跑一遍，再在同一台机器上把全部二进制换成 amd64v3 重跑对照。结论是：即便在低端/预算级硬件上，amd64v3 带来的性能收益仍相当可观。
关注理由：对做计算栈与平台适配的团队，这条提供了一个重要的反直觉结论：ISA 基线提升的收益并不只属于高端 CPU——低端小核平台同样吃得到，因为 AVX2/FMA 这类能力对向量化代码路径是开关式的，而不取决于绝对算力。可落地的启发有三：① 评估 zeus 相关软件栈时，应把「发行版是否提供 x86-64-v3 及以上基线构建」作为显式选项，尤其在算力受限的入门场景中性价比极高；② 反过来也提醒我们做多基线分发的成本管理——amd64 / v3 / v4 多份二进制会放大构建与验证矩阵；③ 低端平台往往是内存带宽与核数受限，向量化收益会被访存瓶颈稀释，评价时应以端到端工作负载而非微基准为准。

OpenVDB 13.1 引入 SIMD 框架：点传输算法在 AVX-512 上获得 2~4 倍提升
计算 图形
OpenVDB 是 Academy Software Foundation 维护的稀疏体积数据结构与工具库，被 Houdini、RenderMan、Cinema 4D 乃至开源 Blender 等 CGI 软件用于处理稀疏体数据，还曾获得奥斯卡技术成就奖；如今在 2026 年，它终于建立了自己的 SIMD 框架以更好利用现代 x86 ISA 能力。随 OpenVDB 13.1 发布的主要变化是引入面向 ISA 向量化的 SIMD 框架，先在 x86 上提供显式 intrinsics 支持，初期采用 Agner Fog 的 VectorClass Library，覆盖到 AVX-512。当以 USE_VCL=ON 选项构建时，收益相当可观：首批改造的「点传输（point transfer）」算法在具备 AVX-512 的现代 x86_64 CPU 上取得 2 倍到 4 倍性能提升。该版本同时带来 NanoVDB 在 CUDA 资源管理与更快 kernel 上的增强，以及 vdb_tool 命令行程序的改进。
关注理由：对做计算/图形核心库的团队，这条是最好的「老牌标量代码向量化」案例研究：一个拿过技术成就奖、被大量商业 DCC 依赖的成熟库，直到 13.1 才有体系化的 SIMD 框架，说明存量代码里沉睡的向量化空间普遍被低估。三点可借鉴：① 它先用成熟的 VectorClass Library 拿到收益，而不是自研 intrinsics 封装——在 zeus 侧同样应优先复用力学验证过的向量库，把自研预算留给真正特殊的算子；② 收益集中在点传输这类规则访存密集算子（2~4x），与我们做数据搬运/重排/聚合内核的场景高度同构，可作为筛选优化目标的启发式；③ 以 编译开关（USE_VCL=ON）方式引入而非默认开启，兼顾了可移植性与收益，值得作为我们引入新 ISA 路径的发布策略模板。

AMD 提交 SEV-TIO TDISP 补丁：为 EPYC 9006「Venice」打通 PCIe 6.0 机密计算直通 I/O
计算 内核
AMD 发布了面向 EPYC 9006「Venice」处理器的最新一批内核补丁，目标是启用 SEV-TIO TDISP——该能力由 PCI Express 6.0 及更新版本支持。名字很长：Secure Encrypted Virtualization Trusted I/O Trusted Execution Environment Device Interface Security Protocol。其中的 TEE Device Interface Security Protocol（TDISP）由 PCIe 6.0+ 提供，用于在机密计算环境中安全地做直通 I/O 设备分配；在 AMD 这边就是配合其 SEV（安全加密虚拟化）虚拟机使用。本次共 17 个内核补丁发往内核邮件列表，让 guest 能够对支持 PCIe TDISP 规范的设备建立信任，并通过私有内存与该设备交互。值得注意的是，这项工作包含一个通用 TEE Security Manager（TSM），由 AMD 与 Intel、Arm、RISC-V 协作开发，用于处理 TDISP、PCIe 加密、设备证明等各 CPU 厂商实现之间的共性部分。
关注理由：对做加速器与 I/O 数据通路的团队，这条的价值在「设备直通的安全边界正在从软件约定升级为 PCIe 协议级能力」：过去 confidential VM 里把设备透给 guest，加密与可信性靠驱动约定；TDISP 把设备身份证明、私有内存交互、接口安全状态机写进链路层规范，意味着以后加速器要在 confidential 场景被采用，协议支持会成为硬门槛而非可选项。三点需提前布局：① 关注通用 TSM 这一跨厂商抽象层——它能显著降低设备厂商分别适配 Intel/Arm/RISC-V/AMD 的成本，zeus 若要走这条路线，跟进 TSM 比自建更划算；② TDISP 绑定 PCIe 6.0+，说明安全特性与链路代际强耦合，硬件规划时要把代际选择与安全路线一起定；③ 此类能力默认对性能与驱动复杂度都有代价，建议按业务敏感度分级启用，而非全量打开。
