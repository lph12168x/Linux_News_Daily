Vulkan 1.4.363 发布：Intel 新增 VK_INTEL_device_info，把「图形 IP 版本」从设备 ID 猜谜变成 API 契约
图形 GPU 计算
Vulkan 1.4.363 作为本周例行规范更新发布，内容包括规范多处澄清与修复、DMA-BUF 外部内存在 VkMemoryAllocateInfo / VkMemoryGetFdInfoKHR 上的多实例校验规则（multi-instance VUs），以及来自 Intel 的最新厂商扩展 VK_INTEL_device_info。
该扩展的职责非常单一：读取 Intel 图形设备的「图形 IP 版本」（graphics IP block version）。Intel 的图形 IP 版本编码了三层信息——架构世代（architecture generation）、该世代内的发布版本（release）、以及该发布版本的硬件修订号（hardware revision）。Intel 之所以引入它，是因为现有 Intel 驱动暴露的 deviceID 字段并不包含图形 IP 版本，于是应用与游戏不得不自行维护一张「deviceID → 图形 IP 版本 / 世代」的人工对照表，每出一批新硬件就要跟着更新。扩展本体由 Khronos 的 Vulkan-Docs 仓库 commit 560d4305 落地，Vulkan Registry 照例同步更新。
关注理由：这条看着是「又一个小扩展」，但指向的是一类很常见的基础设施债。① deviceID 是厂商私有的不透明编号，图形 IP 版本才是可比较的世代 / 修订信息。把「deviceID → 世代」的映射从应用侧的硬编码表收回到 API 里，本质是把猜谜换成契约——应用不必在每代硬件上市后跟着发版；驱动 / 加载器也不必承诺 deviceID 的稳定性，两边各自独立演进。凡是「靠 ID 映射推断能力」的地方，都应该优先问一句：能不能直接暴露那个真正被需要的语义值？
② 硬件修订号（hardware revision）这一层的价值常被低估。它意味着同一 IP 世代内、同一发布版本下的硅后修订（stepping）也可被区分——当某个 workaround 只对特定 stepping 生效时，这是规避成本最低的粒度，比整代禁用精确得多。我们做加速器 bring-up 与 quirk 管理时，应当把「架构世代 / 发布版本 / 硬件修订」做成三级可查询标识，而不是压成一个型号字符串。
③ DMA-BUF 外部内存的多实例校验规则补强也值得留意。DMA-BUF 是 Linux 图形栈跨驱动、跨进程共享缓冲的基石，也是 GPU 与编解码器 / NPU 之间「零拷贝」交接的公共语言。校验规则越明确，跨厂商共享缓冲的灰色地带就越少——我们做 RDMA 与加速器之间的内存交接时，同样需要把「谁拥有生命周期、谁能改属性、多实例下如何裁定」写成显式规则，而不是依赖各方默认约定。

AI 辅助的 Starling 桌面发布 0.5：加入可步行 3D 海滨城市视图，每块显示器独立相机
显示 display 图形 GPU
Starling 是几个月前出现的 Linux 桌面项目：用 Swift 语言编写、自带 Wayland 合成器、且绝大部分代码由 AI（Claude Code）生成。今天发布 0.5，新增可选的 3D 桌面模式。官方对该模式的描述要点如下：
「Starling 保留熟悉的 2D 桌面，另外加入一座可步行的 3D 海滨城市（walkable 3D waterfront city）。打开控制面板选择 3D Desktop 即可切换视角。城市包含移动的船只、车流与云、钟楼、日落光照，以及 cream / bronze / sage 三色的窗口边框。Chrome、视频播放器、文件管理器、终端等仍是真实窗口，用 Alt + Tab 切换，也可以从侧栏（rail）把实时预览前置；双击窗口外侧标题栏可把视图居中到该窗口；弹窗在场景中跟随其父窗口。
每块显示器拥有自己的场景与相机——在一台显示器上行走、转向或做指针驱动的视差，另一台显示器的视图不受影响；场景渲染共享同一后端，但各输出的相机与渲染目标保持独立。」
本次 0.5 由 Claude Fable 5.1 参与完成。此外，Starling 0.5 新增 Windows 支持：通过 WSL2 + Ubuntu 26.04，并使用 RDP 显示模式。
关注理由：技术看点不在「3D 桌面好不好用」，而在它把多输出合成这件事做了显式解耦。①「场景渲染共享后端 + 每输出独立相机与渲染目标」正是多显示器合成器最难的部分。资源池（场景、纹理、后端上下文）要共享以省显存与状态切换，而每块屏的相机、渲染目标、视差相位必须完全隔离——否则一块屏的输入会污染另一块。这条声明等于把合成器描述成「一组独立相机共同观察同一批真实窗口」，这个模型对我们梳理多屏 / 多 GPU 的渲染同步与状态隔离很有参照价值。
② RDP 显示模式跑在 WSL2 上是另一个信号：Wayland 合成器 + 远程 / 虚拟显示后端正在从特例变成可插拔的常规设计。一旦显示后端可替换，测试就多了一条捷径——远端注入合成器输入、在另一台机器上比对画面，比本地自动化更接近真实用户路径。
③ 它还是「AI 生成系统级代码当前水平」的一个可观测样本。桌面合成器是并发、输入、渲染时序高度耦合的领域，若 0.5 的多屏独立相机在实测中真能稳定，说明 AI 辅助在系统编程上已跨过玩具阶段；若不稳，多半会暴露在跨子系统时序契约上。我们评估 AI 参与内核 / 驱动类代码时，可以把「并行状态隔离」和「生命周期管理」当作两条最该重点审的线索。
④ 历史提醒：这个方向与 20 年前 Sun 的 Project Looking Glass 一脉相承，而那次的教训是——3D 桌面的成败取决于输入映射与性能稳定性，而非视觉炫技。任何把「视图」与「窗口」解耦的设计，最终都会在输入焦点与命中测试上接受检验。

Linux 7.3-rc4 前的关键 x86 修复：Granite Rapids 微码防 MCE、FRED 游戏崩溃、APX/EGPR 与 -march=native 冲突
计算 内核
在 Linux 7.3-rc4 发布前数小时，一批重要的 x86 / x86_64 修复被合入，覆盖三类悬而未决的问题：
其一，Intel Xeon 6「Granite Rapids」服务器微码防护。内核现在会拒绝加载微码版本 0x1000405 及更高版本——除非系统此前已经更新到过 0x1000405。原因是 Intel 说明 0x1000405 引入了后续修订所依赖的内部改动（勘误 GNR98：可能导致 machine check exception（MCE）），披露文件中把内部改动归因于微码间通信接口（inter-microcode communication interface）。该保护同时覆盖早期（early）与晚期（late）微码加载路径，且已标记回移到既有 stable 内核版本。同批还修了 GNR101：Granite Rapids 的 0x1000423 微码中最小运行时微码修订号（minimum runtime microcode update revision）写错。
其二，Intel FRED 在 Panther Lake 上导致部分游戏崩溃 / 冻结（Wine / Steam Play 场景）的修复，也在此批次中一并落地。
其三，CONFIG_X86_NATIVE_CPU（-march=native 优化内核构建）的 APX / EGPR 冲突。即将推出的 Intel 平台搭载 APX（Advanced Performance Extensions），会使用 R16–R31 扩展通用寄存器（EGPRs）；而 Linux 内核尚未准备好使用 APX。问题是 native 优化构建会真的生成 APX 指令并触碰 EGPR，结果在 Intel 自家工程机上「造成混乱」。现在内核在执行 native 优化构建时会显式阻止 APX / EGPR 的使用，直到内核具备支持能力为止。细节见对应 pull request。
关注理由：这批补丁恰好覆盖计算平台稳定性的三个层级：硅固件（微码）、兼容层（FRED 与 Wine）、编译器 ISA 选择（APX/EGPR）。三者出问题的共同点是——不崩在改动的地方，而崩在上层，因此都不能靠单点回归发现。
① Granite Rapids 微码这条最值得团队记录：微码版本之间出现了隐式依赖。Intel 明确写出「0x1000405 带来了后续修订所需要的内部改动」，也就是不能跳版、也不能回退；内核唯一可行的策略是「要么一次跳到 ≥0x1000405，要么整体拒绝加载」。这直接改变运维结论：服务器批量微码升级必须先确认能一次到位，分批 / 增量推进反而可能踩 MCE。任何「固件 / 微码 / 固件表（如 CCS 表、配置 blob）」的版本策略都应显式声明是否存在强制迁移点，不能默认「越新越好」。
② APX / EGPR 与 -march=native 的冲突是教科书式案例：编译器「自动发现新指令」与内核 / 运行时「尚未支持新指令」之间的时间差。凡是依赖 native 推断的构建流水线（包括性能测试用的自编译内核），都应显式钉住 ISA 基线而非放任推断。这与本周其它线索方向恰好互为一组对照：Ubuntu 26.10 引入 amd64v3 基线、GCC 17 支持 RISC-V 的 -mtune=native / -mcpu=native、内核又要压制 native 过度优化——本质都是同一道题：在「性能上限」与「可预期性」之间做显式取舍。结论是 ISA 选择必须是显式配置项，而不是编译器的默认猜测。
③ FRED 这条延续上周的线索。新的中断 / 异常投递机制会改变内核栈与异常上下文的构建方式，凡绕过标准调用约定、直接使用原始 INT 指令的历史代码（如 Wine 的旧实现）都容易被击中。新硬件特性上线时，兼容层（Wine / 虚拟化 / 转译层）是必须提前纳入回归的「第三类负载」——既不是内核自身测试，也不是普通应用测试，却最常见地把新特性打回。

Linux 7.3-rc4 发布：LLM 抓到的修复合计偏多，Linus 点名「文件系统整体被重新审视」
内核 计算
Linus Torvalds 宣布发布 Linux 7.3-rc4。近几个月修复量依然很大且分散，其中很大一部分由 AI / LLM 发现各类代码缺陷驱动；不过 Linus 表示对 7.3-rc4 并不太担心。本周合入的内容包括：一批重要 x86 / x86_64 修复、XPad 驱动新增多款游戏手柄支持、修两个显著的 Btrfs bug，以及修一个自 2023 年起就存在的用户态静默数据丢失 bug。
Linus 在公告中的要点：「我们都知道套路了：它很大，等等等等。我觉得有点意思的是，文件系统在「比往常更大」里占了相当显著的一部分。这次是 smb 和 ntfs——所以并不是某一个文件系统的问题，而是文件系统整体近来都得到了更多关注。当然，驱动改动仍是最大头，只是不像有时那样压倒性：整个补丁大致是三分之一驱动、三分之一文件系统与网络、三分之一「杂项」（架构修复与工具链）。但大多是相当小的补丁。我认为其中最大的单个补丁，是删掉一个在合并窗口里从 lib/ 移到 mm/ 的文件——旧副本不知为何留了下来，于是有了这个迟到的删除补丁。」
他补充：shortlog 里没有特别有意思的东西，有大量错误路径清理（error path cleanup），而各种 LLM 在这类问题上似乎相当擅长，只是这类修复通常在日常使用中并不明显——「但话说回来，如果这些问题正好砸到你，你就会很在意」。Linux 7.3 将于 10 月发布。
关注理由：这条的价值不在版本号，而在于它给出了一个可观测的趋势：① AI / LLM 正在实质性改变内核修复的构成。修复总量变大，且集中在错误路径清理这类「低发生概率、高代价」的地方。这恰好补上了人工评审的系统性盲区——人天然倾向于审「正常路径」，因为那才是脑中的主流程。对我们的启发是：把 LLM 辅助审查定位为「穷举不会走到的分支」，与现有 CI、fuzz、静态分析形成互补，而不是替代；评估其收益时也不要只看「主路径性能」，而应统计被拦截的未触发缺陷数。
② Linus 对「文件系统占比升高」的观察值得记：不是某个 fs 的问题，而是当一类代码被系统性地重新审视时，缺陷密度会先上升、再下降。团队做代码质量专项时要预期「先看到更多 bug」这个阶段，不要把缺陷数上升误判为质量恶化，也不要因为数字难看而提前收工——真正的收益在后面。
③「最大单补丁是删除一个遗留副本」这个细节像玩笑，实则是跨目录重构的经典失误模式：文件搬迁时旧路径残留，构建仍然通过（或恰好不影响），于是静默存活数月。做大规模文件 / 模块搬迁时，这类「半完成搬迁」需要用构建产物清单或树内断言来兜底，而不是靠人工 diff 复查。
④ 结合 rc4 里那个「2023 年至今的静默数据丢失 bug」，这一周的共同关键词是「不报错的错误」。对存储 / 传输类系统（含我们关注的 RDMA 数据路径），静默错误永远比显式失败更需要专项手段——端到端一致性校验、定期主动巡检、以及「错误必须可观测」的设计约束，三者缺一不可。

KDE 公布 2026–2028 三大目标：Ocean 设计系统 + Union 主题引擎的「下一代样式」居其一
显示 display 图形 GPU
正在奥地利 Graz 举行的 KDE Akademy 2026 上，KDE 公布了未来两年（2026 及以后）开发者将额外投入精力的三个目标：
1）KDE for Enterprises and Deployments（面向企业与部署场景）。工作项包括 Plasma 中更好的 LDAP 集成、口令过期（password expiry）支持、基于 SSO 的账户与登录、改进的网络打印机设置、以及良好的无头远程 / 终端支持等，目标是让 KDE Plasma 在企业部署中真正可用。
2）更好的文档（Better documentation）。清除过时、误导、重复的文档，整体改进教程与 KDE 桌面相关文档，并包含创建一份贡献者指南（contributor guide）。
3）面向 KDE 的下一代样式（Next Generation Styling for KDE）。设计师将在 Ocean 项目上构建一套设计系统（design system）并据此打造统一设计；同时技术侧（technical stakeholders）推进 Union 主题引擎本身。
全部提案与工作项可在 invent.kde.org 的 goal-setting 2026 看板查看。
关注理由：① 最有工程价值的一条是「下一代样式」的组织方式：它把「设计系统（Ocean）」与「主题引擎（Union）」明确拆成设计侧与技术侧两条并行线。这是个正确的解耦——如果视觉规范与渲染 / 主题引擎绑在一起演进，任何一方改动都会卡住另一方，最终只能靠特例打补丁。把引擎当作可独立收敛的基础设施、把设计系统当作引擎之上的配置层，第三方主题与上游才能并行迭代。这个分层思路可以直接借到任何「外观 / 皮肤 / 视觉规范」类系统上，包括我们自己的可视化与工具链 UI。
②「KDE for Enterprise」的目标清单里，LDAP、口令过期、SSO、无头远程全是「把桌面当作企业托管终端」的门槛项，而不是美观项。桌面环境要在企业里替代 Windows / macOS，胜负点就在这一栏。其中「无头远程 / 终端支持」尤其值得堆栈方向留意：它意味着 Wayland 合成器的远程与虚拟显示后端要从特例变成一等公民，这与本周 Starling 走 RDP 显示模式、以及 GNOME 侧远程支持的动作是同一个方向。
③「清理过时 / 误导 / 重复文档」被选进三大目标，说明长期演化项目已把文档腐化当作工程质量问题来处理。这也侧面印证了 AI 时代的一个变化：文档的「可被机器消费的正确性」本身开始产生价值——LLM 会读文档并据此生成代码或操作步骤，过时文档的代价比过去高得多。我们维护内部知识库时，也应把「过时」当作缺陷来报告，而不是风格问题。
④ 三个目标分别对应可运维性、可学习性、视觉一致性，都不是新功能，而是把已有能力补齐成体系——这是成熟桌面项目进入「收敛期」的典型选择，也说明 KDE 判断自己当前的主要风险来自内部一致性而非功能缺口。

Plasma 6.8 进入打磨期：回归清单仅剩 5 项（多为多屏错位），KWin 修两处崩溃；6.9 已起步
显示 display 内核
Plasma 6.8 beta 发布后，KDE 桌面开发者本周主要在做 bug 修复，以及对 Plasma 6.9 的一些早期改动。6.8 beta 的测试情况相当不错：当前回归列表（regression list）只有五个 bug，分别是注销界面失去焦点、通知错位、多显示器下注销 / 重启 / 关机浮层错位，以及 「切换用户」行为异常。
本周 Plasma 变更包括：Plasma 6.8 新的 Kup 备份方案现在会显示已用时间，且平均速度信息更准确；KDE 桌面 portal 对话框在 6.8 得到进一步打磨；Plasma 6.8 不再每次显示通知都写一次缓存文件。
修复方面：Plasma 6.7.6 修了一个 KWin 在用 Alt + Tab 切回游戏时偶发崩溃的问题；Plasma 6.8 修了 KWin 在特定方式操作标题栏按钮时崩溃的问题。
Plasma 6.9 方面：在桌面上重命名文件或文件夹时，如今会在必要时显示全部标准警告与确认——例如隐藏文件 / 文件夹的警告，或变更文件类型 / 扩展名时的提示。
关注理由：① 这一周真正的看点不是修复数量，而是「回归清单的构成」：五项里三项是「错位 / 焦点」类，且集中在注销界面与多显示器场景。这类问题恰恰是新合成器 / 新渲染路径最典型的副产物——布局与焦点的状态机在输出数量或拓扑变化时失真。这与本周其它线索（GNOME 51 的帧调度与背景模糊协议、Starling 的每输出独立相机）指向同一个结论：做多屏 / 多输出图形系统时，「输出拓扑变化时的 UI 状态机」应当被划成独立的回归域，而不是塞在普通用例里顺带测。热插拔、分辨率变更、主屏切换、缩放切换，每一项都应有一条专门的自动化路径。
②「不再每次显示通知都写一次缓存文件」是个小而典型的性能修复：高频通知 × 磁盘写 = 无谓 I/O 与闪存磨损。它提醒我们，桌面与系统层的性能优化很大一部分并不在渲染管线，而在于把无意义的持久化动作删掉。同类思路（取消高频小写、状态留在内存、批量合并落盘）在我们优化数据路径与日志路径时同样适用——先问「这次写盘真的必要吗」，往往比调优 IO 栈收益更大。
③ 两个 KWin 崩溃修复（Alt + Tab 切回游戏、标题栏按钮交互）都落在「输入与窗口状态的并发」上，属于合成器最难测的一类，需要特定交互顺序与时机才会触发。这提示我们的图形 / 显示自动化必须覆盖「输入序列 + 窗口状态切换」的组合，而不只是比对渲染结果——只有像素断言、没有交互序列断言的测试，是发现不了这类崩溃的。
④ Plasma 6.9 提前引入重命名时的完整警告 / 确认，是在补「行为可预期性」：默认不静默改动用户文件的语义。这种「先提示、再动作」的保守取向，与内核 / 文件系统侧避免静默错误的思路完全一致——凡是可能改变数据含义但又不易被察觉的操作，都值得付出一次打扰的代价。
