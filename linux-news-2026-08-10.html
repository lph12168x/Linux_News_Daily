Mesa 26.3 为 Intel 新 GPU 启用 Large GRF 大寄存器模式
GPU
Mesa 26.3-devel 的 Intel 图形编译器代码本周为 Alchemist/DG2 与 Battlemage/Xe2 启用 Large GRF（大通用寄存器文件）模式，并为 Xe3 通过新的 Variable Register Thread（VRT）功能开放 256 个 GRF 寄存器。Large GRF 把单个硬件线程的寄存器空间从 128 翻倍到 256 个 GRF 寄存器，核心作用是减少寄存器溢出（register spilling），从而改善着色器/计算内核的执行效率；Large GRF 此前已在 IGC / Intel Compute Runtime 启用，本次是将其带入 Mesa 的 ANV（Vulkan）与 Rusticl（OpenCL）开源栈（合并 MR !43588）。
关注理由：GRF 是 Intel GPU 执行模型的核心资源，减少溢出直接利好游戏与计算负载的寄存器压力；把 Large GRF/VRT 带进 Mesa 开源驱动，意味着 DG2/Battlemage/Xe3 用户在 ANV、Rusticl 上也能吃到上游化的寄存器优化，是 Intel Linux 图形栈持续补齐底层能力的一环。

Linux 7.3 的 TTM 显存管理将更激进（Valve 主导，cgroup 保护）
GPU 内核
本周提交给 DRM-Next、排队等待 Linux 7.3 合并窗口的 drm-misc-next 收尾材料中，最值得注意的是 TTM（Translation Table Maps）显存管理在保护限额下分配时变得更「激进」。这项由 Valve 开源 Linux 图形团队 Natalie Vock 主导、历经八轮修订的改动，解决了设备内存（dmem）保护在 VRAM 紧张时失效的问题：未受保护的应用会先填满 VRAM，迫使 TTM 把受 cgroup 保护的应用分配回退（back off）到 GTT。新逻辑下，受保护分配会改为主动驱逐未保护缓冲区来腾出空间（仅受保护分配可驱逐未保护者，杜绝乒乓），确保应用真正用满系统授予的内存保护。该系列还带来 DMEMCG 驱逐支持，并已在 AMDGPU 与 Xe 驱动启用；UDMABUF 移除了 Xaver Hugl 在多 GPU/eGPU 工作中发现的 64MB 人为限制；Nouveau 也获得 Natalie Vock 写的 DMEMCG 支持。
关注理由：这是面向「低显存设备游戏体验」的关键内核态改进，Valve 持续在 Linux 图形内存管理上投入。对只有 8GB 显存的独显或核显用户，更激进且带 cgroup 保护的 TTM 驱逐逻辑能显著减少「显存被挤占→回退 GTT→卡顿」的尴尬，是中低端硬件上流畅运行游戏的基础设施。

Vulkan 1.4.359 扩展协作矩阵能力（NVIDIA/Qualcomm/Intel/Arm 共推）
GPU 计算
Vulkan 1.4.359 本周发布，带来新扩展 VK_EXT_cooperative_matrix_maintenance1，对 2023 年 VK_KHR_cooperative_matrix 引入的协作矩阵能力做了一系列补强。协作矩阵可用于机器学习推理、图形后处理、物理仿真等；新扩展把能力从「简单 GEMM 内核」扩展到类型/用途转换（type/use conversions）、归约（reductions）、逐元素操作（per-element operations），以及元素索引到矩阵坐标的转换，并新增查询协作矩阵属性的命令（可输入期望 subgroup size 与本地工作组大小，便于未来扩展）。该协作矩阵更新由 NVIDIA、Qualcomm、Intel、Arm 工程师共同完成。
关注理由：协作矩阵是 GPU 上做矩阵乘（AI/ML 与科学计算的核心原语）的高效路径，本次维护扩展让它从「只能跑 GEMM」走向更通用的矩阵运算，并打通了与 subgroup/工作组规模相关的属性查询，直接利好跨厂商 GPU 上的 ML 推理与图形后处理性能与可移植性。

KDE Plasma 6.8：UI 打磨 + 内置远程桌面服务器修复
显示
距离 10 月 Plasma 6.8 发布又一周，This Week in Plasma 汇总了面向 6.8 的一系列改动：向不可用打印机打印时弹出通知（不再静默失败）；任务管理器缩略图在标签上方留出更舒适的内边距；新建用户时对用户名/密码等限制给出更清晰的 UI 提示；内置远程桌面服务器修复了某些客户端出现黑屏的问题，并在网络不佳时降低延迟、提升表现；剪贴板弹出改为按需加载（而非启动时加载）以减少内存占用。
关注理由：这些改动中，内置远程桌面服务器的黑屏修复与弱网低延迟优化最实在——Wayland 下远程桌面（RDP）一直是痛点，KDE 持续打磨意味着 Linux 桌面在远程办公/协助场景的可用性进一步提升；其余 UI 细节则体现 Plasma 6.8「打磨体验」的发布基调。

Intel 内核驱动推进 HDMI 2.1 FRL（Meteor Lake 及更新平台）
显示 内核
继 AMD 之后，Intel 也放出了面向其内核图形驱动的 44 个补丁，为 Meteor Lake 及更新平台带来 HDMI 2.1 Fixed Rate Link（FRL）支持，以突破 TMDS 上限、支持更高刷新率与分辨率。这组补丁目前是「进行中」状态：已在 Panther Lake（PTL）上轻量测试，4K@120 可用；但 DSC（显示流压缩）尚未实现，故 8K 等更高分辨率模式暂不支持，测试也仅限于 MTL/PTL。Intel 2022 年曾有过 HDMI FRL 补丁但此后冷却，本次重燃或反映 HDMI Forum 在开源驱动支持态度上的变化。预计最快随 Linux 7.4 周期上游化（连同 DSC 支持）。
关注理由：HDMI 2.1 FRL 是 4K@120/8K 等高带宽显示 mode 进入开源 Intel 驱动的前提，此前长期卡在 TMDS 限制。Intel 重新推进并与 AMD 同期发力，意味着 Intel 核显/独显用户未来在高端显示器上也能吃满高刷；不过 DSC 缺失意味着 8K 仍需等待，属于「地基先铺好」的进展。

Wine 11.15 发布：修复 Wayland 双重 sRGB 灰屏与全屏偏移
显示
Wine 11.15 于周六（打破通常的周五双周节奏）发布，带来 41 项已知 bug 修复，其中两处与 Wayland 相关：修复 Wayland EGL 代码因双重 sRGB 转换导致色彩发灰（washed-out）的问题，以及修复 4:3 全屏应用在 Wayland 上内容偏移的问题。其余改动包括 BCrypt 更多 KDF 算法、MinGW 模式下的 ARM64EC 构建、WindowsCodex 更多格式转换、本地 NTLM 认证（msv1_0 支持进程内 NTLM 并可回退 ntlm_auth）。最吸睛的是修复了可追溯到 2006 年 3 月的 Bug 4811——一个 MSXML3 的 XMLDOMDocument 问题，时隔二十年终于解决。
关注理由：Wine 的 Wayland 驱动仍在快速成熟期，双重 sRGB 导致的「色彩发灰」与全屏偏移都是直接影响观感的显示问题，本次修复让 Linux 上跑 Windows 游戏/应用的画面更准确。二十年老 bug 的终结则是 Wine 项目「清债」式维护的注脚，印证其稳定性持续改进。

Apple M3 Pro / Max / Ultra 设备树上游化，瞄准 Linux 7.3
计算 内核
Linux 7.2 已合入基础 Apple M3 SoC 的设备树（DT）支持（但距离日常可用仍有大量功能缺失），现在面向即将到来的 Linux 7.3，M3 Pro、M3 Max、M3 Ultra 变体也将获得初始的引导支持。本次同样是基础的 DT 文件（由 Sven Peter 提交的 pull），把支持带到与基础 M3 SoC 大致相同的水平——尚不能用于终端用户，GPU 加速等大量功能仍未支持，只是为未来内核版本铺路。该 pull 还包含面向 Apple M1/M2 系列的 HWMON 传感器支持（应对 Apple「混乱的传感器」）。M3 Pro/Max 于 2023 年底发布，M3 Ultra 随 2025 年 3 月的 Mac Studio 到来；主线内核何时能对 M3 系列提供可用日常支持仍不明朗，在那之前用下游 Asahi Linux 发行版仍是更现实的选择。
关注理由：这是 Apple Silicon 主线化的又一块基石——从 M1/M2 到 M3 基础版再到 M3 Pro/Max/Ultra，逐代把设备树铺进主线。虽然距离「可用」还很远（GPU 加速缺失），但它持续扩大开源社区对 Apple 硬件的覆盖广度，也为 Asahi 之外「纯主线内核」的长期目标积累基础。

PoCL 7.2-RC1：在 RISC-V 与 x86_64 上拿下 OpenCL 3.0 一致性
计算
PoCL（Portable Computing Language，OpenCL 的便携实现，可走 CPU 执行或经 LLVM 后端用于 Level Zero、NVIDIA GPU 乃至远程设备）的 7.2 候选版发布，达成官方 OpenCL 3.0 一致性（conformance）：现已在 RISC-V 与 x86_64 处理器上通过 Khronos OpenCL CTS 验证——RISC-V 一致性测试在 Star64 开发板与 Milk-V Jupiter 上完成，x86_64 则在 AMD Ryzen 9 9900X 上提交。PoCL 7.2 还新增一批扩展（cl_khr_extended_bit_ops、cl_khr_device_uuid、cl_khr_integer_dot_product、cl_khr_kernel_clock 等），并兼容到 LLVM 22（NVIDIA CUDA / Intel Level Zero 设备），CPU 后端更可兼容 LLVM 22 与 23。
关注理由：OpenCL 是 CPU/GPU 异构计算的事实标准，PoCL 在 RISC-V 上拿下 OpenCL 3.0 一致性，意味着开源 RISC-V 平台也能跑标准 OpenCL 计算负载——对 RISC-V 进入边缘/异构计算意义重大；同时 PoCL 持续追平 LLVM 与新扩展，巩固其作为「跨架构 OpenCL 便携实现」的地位。

AMD ROCm 新组件 Spur：AI 原生、Rust 编写的 GPU 任务调度器
计算
AMD 开源 GPU 计算栈 ROCm 迎来新组件 Spur：一个 AI 原生、用 Rust 编写的任务调度器，面向把 GPU 负载扩展到数千 GPU 集群。Spur 被描述为 AI-native job scheduler，使用 Rust、提供 WireGuard 网状网络、GPU-first 调度，并对 Slurm 的 CLI / REST API / C FFI 即插即用兼容；设计上还提供现代状态管理，所有状态在重启后存活。AMD 的 Anush Elangovan 公布 Spur 可处理数千 GPU 集群，并计划将其扩展到大型 CPU 集群；代码以 Apache 2.0 许可托管于 ROCm/spur。
关注理由：随着 ROCm 向大规模训练/推理集群延伸，原生的 GPU-first 调度器是补齐生态短板的务实一步——用 Rust 写、兼容 Slurm、内置存活状态，降低了把 ROCm 用于超大规模部署的门槛。对 AMD 想在 AI 集群市场与 NVIDIA 竞争而言，Spur 是「软件栈完整性」上的增量投入。
