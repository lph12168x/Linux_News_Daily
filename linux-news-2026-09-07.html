AMD 组建精英团队把 Rust「深入 GPU 栈」：从固件、运行时到编译器与 GPU 架构
图形 计算
AMD 资深 Fellow Harsh Menon 本周在 LinkedIn 公布，AMD 正在组建一支「精英小队」，把 Rust 代码「深入 GPU 栈」——覆盖编译器、运行时、固件、GPU 架构与软硬件协同设计。配套招聘帖明确：Rust 是该方向的核心技术选型，工作横跨编译器与工具链、底层 GPU 软件、固件、开发者工具，以及提升复杂软硬件系统安全性与正确性的方法；工程师将影响 AMD 当前与未来平台在中近期实现和长远架构上的 Rust 用法。
值得注意的是，AMD 并非孤例——NVIDIA 也在推进类似的 Rust 化 GPU 软件计划，包括用 Rust 编写的 Nova Linux 内核驱动。
关注理由：对做加速器/图形驱动栈的团队，这是信号级变化——两大 GPU 厂商同时在把 Rust 推进到性能敏感、高信任的底层（编译器、固件、运行时）。可借鉴点：其一，Rust 进入 GPU 栈的优先级已从「实验」升到「招聘建制化」，意味着未来内核图形驱动（Nouveau/Nova/AMDGPU 的 Rust 部分）和工具链会持续受益；其二，AMD 把「编译器 + 运行时 + 固件 + 架构」打包协同，正是团队在 zeus 架构上「软件栈整体推进、而非单点改驱动」的思路镜像。即便短期不直接用 Rust，也要跟踪其 ABI/接口约定是否会外溢到用户态（如 shader 编译器、固件加载协议），影响我们与上游驱动的对接方式。

NVIDIA 为开源 Nova 提交 vGPU 管理器与 VFIO 变体驱动：workstation / 数据中心 GPU 的虚拟化路径
图形 计算
NVIDIA 在邮件列表抛出一组 13 个补丁，为上游的 Nova 开源内核图形驱动引入 NVIDIA vGPU 管理器与 VFIO 变体驱动。其目的是在运行于上游 Nova 驱动之上的前提下，启用 vGPU 管理，并支持 QEMU 上的 Linux / Windows 客户机走 VFIO。
作者提醒：看到「VFIO + GPU」先别激动——首批支持的更可能是 NVIDIA 的工作站与数据中心产品，而非消费级 GeForce。Nova 驱动仍在向主线内核成熟推进，端到端可用尚需时日。
关注理由：Nova 是 NVIDIA 用 Rust 重写、面向未来的开源内核图形驱动，本次补丁把虚拟化（vGPU / VFIO）能力补齐，意味着开源栈正从「能显示」走向「能进云 / 虚拟化场景」。对做计算/加速器虚拟化的团队，两点值得记：其一，NVIDIA 把 vGPU 控制面先落在开源 Nova 上，方向是把数据中心 GPU 的切分/虚拟化能力逐步开放给主线内核——这与 RDMA 设备虚拟化（如 SR-IOV、VF 直通）的演进路径可对照；其二，目前明确偏向 workstation/datacenter 而非消费级，评估其在我们环境的可落地性时要先确认硬件代次。

Nouveau 落地 Blackwell 显示修复、迈向 HDMI 2.1：GSP 显示路径与 vblank / infoframe 修复
显示 图形
在周日的 Linux 7.3-rc2 之前合并的一批 DRM 修复中，开源 Nouveau 驱动拿到了多处面向当代 NVIDIA Blackwell（GB20x） GPU 的显示修复：改善与 GSP（GPU System Processor）的交互、修复 HDMI vendor infoframe、修正 HDMI GCP AVMute 寄存器偏移、修复 Blackwell 上的 vblank 中断等。
开发者 Mohamed Ahmed 说明，这些修复大多是在推进 Nouveau 的 HDMI 2.1 支持过程中产生：它们为 FRL、DSC、VRR 等高级特性打底——例如 2.147GHz 像素时钟上限这类问题虽当下不触发，但必须先修掉才能解锁后续特性。
关注理由：开源 NVIDIA 驱动长期卡在「显示基础不稳」上，这次修复把 Blackwell 的显示链路（GSP 协同、infoframe、vblank、像素时钟）清理了一遍，是 HDMI 2.1（FRL/DSC/VRR）的前置地基。对做显示栈的团队，可借鉴其节奏：先补「看似不触发」的底层约束，再开高级特性——FRL/DSC/VRR 这类高带宽显示特性，往往被像素时钟上限、infoframe 偏移等「安静的 bug」挡住。这与团队在 zeus 显示能力上「先稳链路、再上高刷新 / 高色深」的推进顺序一致。

Mesa 26.3 准备 Intel Nova Lake P 的 64 位 GPU 寻址：Xe3P 成 Intel 首款支持 64 位地址的 GPU
图形
合并进 Mesa 26.3 的 49 个补丁，改动 Intel 图形编译器代码与 ANV（Vulkan）驱动，引入「efficient 64-bit」寻址模式。背景：到 GFX35 为止，Intel 用 32 位地址 + 64 位堆基址拼出完整地址；而 GFX35+（Nova Lake P / NVL-P 的 Xe3P 核显）起，EU 原生支持 64 位地址——NVL-P 可通过 STATE_BASE_ADDRESS 的位选择寻址模式，更新的 GPU 将只支持 64 位。
本次合并覆盖编译器与 ANV 的高效 64 位状态下发；后续 MR 会补上 Iris（OpenGL）驱动支持。该变化不影响其他 Nova Lake 变体（S/U/H/HX 在 Mesa 上已被当作稳定支持）。
关注理由：这是 Intel 集成显卡架构级变化——Xe3P 是首款 EU 原生支持 64 位地址的 GPU，且后续代次只支持 64 位。对做图形/计算栈的团队，含义是：其一，64 位 GPU 寻址会改变缓冲区/堆的管理模型（不再依赖 32 位偏移 + 基址拼接），大型分配、GPU 直访大内存（与 RDMA/统一内存思路相通）会更直接；其二，Mesa 侧 ANV 先落地、Iris 跟进，提示我们若对接 Intel 新核显，Vulkan 路径会先于 OpenGL 具备新能力，兼容性评估要以 ANV 为优先参考。

Vulkan 1.4.362 发布：Valve Linux 图形团队贡献 VK_KHR 与 VK_VALVE 两个新扩展
图形 计算
Vulkan 1.4.362 例行更新带来两个由 Valve Linux 图形团队主导的新扩展：
① VK_KHR_pipeline_library_group_handles——允许直接从 pipeline library 查询 group handles，提升与 DXR 1.1 规范的兼容性（合作方含 AMD、Igalia、Intel、NVIDIA）；
② VK_VALVE_buffer_device_address_allocation_alignment——允许指定 buffer device address 分配的对齐，主要为 Valve 的 VKD3D-Proton 这类 D3D12 兼容层服务：某些 D3D12 应用依赖比实现默认更大的地址对齐，对齐收紧会导致异常行为。
关注理由：这两个扩展都是为「在 Linux 上把 Windows / D3D 负载跑顺」服务的——DXR 1.1 兼容关乎光线追踪，buffer device address 对齐关乎 D3D12 层（VKD3D-Proton）的稳定性。对做计算/图形栈的团队，值得记两点：其一，上游图形生态仍在持续为兼容层与跨 API 映射补细节（对齐、handle 查询），这类「看似边角」的扩展往往决定一个实际游戏/应用能否跑通；其二，Valve 在 Linux 图形栈的话语权持续走强，VK_VALVE 厂商扩展的出现说明关键能力会先以厂商扩展形式落地——我们评估新 GPU/驱动时，应把「Valve 相关扩展支持度」纳入兼容性清单。

Apple A18 Pro / MacBook Neo 初步 Linux 支持补丁发布：先跑通单核与最小设备树
计算 内核
开源开发者 Yureka Lilian 在周五贴出初始 Linux 补丁，为 Apple A18 Pro（t8140 SoC，即 iPhone 16 Pro 同款）与低价位 MacBook Neo 笔记本建立设备树与绑定。补丁仅含 CPU 核心、中断控制器、看门狗、串口与 framebuffer 的最小设备集合；当前甚至只能跑在单核上（受 WFI/WFIT 指令限制），距离日常可用还远。
除内核改动外，Asahi Linux 的 m1n1 bootloader 也需相应修改。这仅是 MacBook Neo 在 Linux 上「跑顺」漫长进程的第一步。
关注理由：这是 Apple Silicon 在 Linux 上的又一次「从零起步」——和 M3 初期一样，先以最小设备树 + 单核起步。对团队的价值在于参照其移植方法论：其一，新 SoC 的 Linux 支持遵循「设备树 + 绑定先行、最小外设、逐步解锁多核/显示/GPU」的固定路径，可作为我们评估新硬件平台 bring-up 成本的模板；其二，目前仅 framebuffer（无加速 GPU），提示 Apple Silicon 的图形/计算加速仍是最大缺口——这与我们在新加速器平台上「先点亮、后加速」的节奏一致。对做 ARM/异构计算的同学，A18 Pro 的 SMP 起步方式（WFI/WFIT 限制）也值得对照。

KDE Plasma 6.8 落地 Windows 风自动滚动、Breeze 主题降 vRAM 占用
显示
面向 10 月中稳定版（恰逢 KDE 项目 30 周年）的 Plasma 6.8，本周落地多项改进：Windows 风「自动滚动」——中键进入滚动模式、用指针方向控制滚动，且新增开关可切换「按住 / 点按」两种触发方式；新增远程桌面「独占模式」——连接时锁定对端物理屏、改显新建虚拟屏；Spectacle 等 KPipeWire 应用录屏画质提升；Breeze 主题优化 SVG 资源、降低 vRAM 占用（对显存紧张设备友好）；并补齐 Wayland 下 dwell clicker 等无障碍能力。
关注理由：Plasma 6.8 的两条与「显示 / 资源」直接相关——其一，Breeze 省 vRAM 对显存受限的集成显卡 / 嵌入式 / 加速器载板是实打实的收益，提示桌面环境正把 GPU 显存当稀缺资源精细管理，这与我们在低显存设备上跑合成器/可视化要「抠显存」的做法一致；其二，录屏画质提升 + 远程桌面虚拟屏 / 独占模式增强了 Wayland 下的屏幕共享与远程能力，对做显示/串流栈的团队，Wayland 屏幕捕获与远程桌面的可用性正快速补齐，评估远程/协作方案时可优先看 Plasma 6.8 的 KPipeWire 路径。
