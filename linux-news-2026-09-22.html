AMD 开始为 GDDR7 显卡铺路：AMDGPU 新增 GDDR7 显存标识，同步引入 IH 8.0 与 NBIF 7.10
图形 GPU 内核 kernel
AMD 今天送出最新一批 Linux 内核图形驱动补丁，用于启用若干新的硬件 IP 块，其中一项直接指向下一代的 GDDR7 显存。
最明确的一处改动是：补丁为 AMDGPU 驱动新增「GDDR7」作为显存类型标识（video memory name）。当前一代 AMD RDNA4 显卡仍使用 GDDR6，而 NVIDIA GeForce RTX 50 桌面卡已经在用 GDDR7；业界普遍传闻下一代 RDNA5 将切到 GDDR7。所以这条本身不算意外，但它把近期零散的 AMDGPU 补丁串成了同一条时间线——即这些新 IP 很可能就是 RDNA5 的组成部分。
同一天送出的还有两组 IP 启用补丁：中断处理器 IH 8.0（Interrupt Handler 8.0），以及新版总线接口 NBIF 7.10（New Bus InterFace）。此外还有若干较小的铺垫性补丁。这一批工作延续了此前 Display Core Next 6（DCN6）与 GFX 13.0.x 的推进节奏。
针对消费级 GPU 的开源驱动启用工作，明显远早于硬件上市。近期传闻称受行业供应紧张影响，RDNA5 可能在 2027 年只先出少量 SKU，更多型号要等到 2028 年。
关注理由：这条的价值在于看时间线，而不是看单个补丁。① 显存类型的「标识」是 bring-up 的早期信号。把 GDDR7 作为一个显存类型枚举加进去，意味着驱动内部的显存容量 / 时序 / 初始化路径已经开始为这个介质分支——这类改动通常出现在流片后、量产前的早期阶段，比规格表泄露更可靠。跟踪上游提交，往往能比公开路线图更早看到硬件的实际配置。
② 把「IP 版本号」当作路线图来读。IH 8.0、NBIF 7.10、DCN 6、GFX 13.0.x 这几个数字是相互独立的推进轴——中断控制器、总线接口、显示核、图形核各自演进。当我们给加速器做驱动适配时，同样应该把自己平台的 IP 版本矩阵整理出来，明确「哪一版配对哪一版」，而不是把整颗芯片当成一个整体版本号来管理。这样在出现某一路径回归时，能快速定位是哪个 IP 的行为变化。
③ 「启用工作前置到上市前两年」这件事值得团队内化。开源驱动的价值不只是合规或社区形象，而是它逼着硬件与固件团队提前把寄存器语义、电源序列、错误处理路径写成可被别人读懂、可被上游评审的形式。这个副作用本身就是设计评审。我们做 zeus 与 RDMA 栈时，也应当尽量把内部约定提前外化为接口文档与可验证的补丁切片。

Valve 在 Steam 客户端 Beta 推出 Pyrowave 视频编解码：带宽 5~10 倍换取极低延迟，面向千兆局域网串流
显示 display 图形 GPU
今天更新的 Steam 客户端 Beta 引入了一个实验性视频编解码 Pyrowave，定位是高带宽、极低延迟的视频串流。它已随本次 Beta 一起提供，覆盖 Windows、macOS 与 Linux（Linux 侧需要使用实验性的 SteamRT3 客户端）。用户可在 Steam Remote Play 的高级客户端设置中启用。
关键参数：
· 带宽约为其他串流编解码的 5~10 倍，因此明确面向 局域网场景，建议至少千兆以太网；
· 基于 Vulkan API 实现；
· 设计目标为极低延迟；
· 支持 HDR 与 YUV 4:4:4（无色彩子采样损失）。
该编解码由 Hans-Kristian Arntzen 开发——他正是 VKD3D-Proton 的核心作者（VKD3D-Proton 是把 D3D12 翻译到 Vulkan 的项目，直接支撑了 Steam Play / Proton 上的大量 Windows 游戏）。本次从「翻译图形 API」跨到了「视频编码器」，其技术取向一脉相承：直接吃 Vulkan、把开销压到最低。
关注理由：这条是「显示 / 串流」方向少见的协议层创新，几个点值得注意。
① 这是对「带宽换延迟」的一次正面押注。主流串流编解码（H.264/H.265/AV1）的优化目标长期在「同画质下更省码率」，代价是编码器内部引入更深的参考帧依赖与更大的缓冲，而缓冲深度直接等价于端到端延迟。Pyrowave 反向操作——接受 5~10 倍码率膨胀，换掉几乎全部编码缓冲。在千兆局域网已经普及、而「无线串流手感」仍是痛点的当下，这个取舍成立。凡是做实时交互链路，都该先问一句：瓶颈到底是带宽还是延迟？两者经常被混为一谈，而它们的解法是相反的。
② YUV 4:4:4 与 HDR 同时支持，说明目标不只是游戏串流。4:4:4 对文字、UI、细线、彩色边缘的保真至关重要——这正是办公、远程桌面、开发与设计场景的核心诉求，而这些场景在 4:2:0 下会明显发糊。把它理解成「局域网内的高保真远程显示通道」，比「游戏串流编解码」更接近它的上限。
③ 用 Vulkan 做编解码的路径值得关注。传统视频链路走 VA-API / V4L2 等专用接口，跨厂商抽象层厚、特性对齐慢。若编码器直接建立在 Vulkan 计算之上，就能复用同一套队列、同步原语、外部内存与零拷贝路径，与渲染管线天然贴合。这与我们在加速器上把「计算」与「数据搬运」统一到同一套调度原语上的思路是一致的——减少层次，往往同时减少延迟和胶水代码。

Gravity Linux 首个 Early Alpha 发布：专攻 Apple M4 及更新机型，M4 Mac Mini 上跑起 OpenGL 3.3 GPU 加速
显示 display 图形 GPU
一个新的 Linux 发行版 Gravity Linux 出现，专注 Apple Silicon Mac 上的 Linux 支持。它是 Fedora Remix 的一个分支（spin），瞄准仍处于实验性支持状态的 Apple M4 及更新机型。项目除了复用 Asahi Linux 的代码与逆向工程成果之外，也借助 OpenAI Codex 与 Claude Code 参与开发。
本次发布 Early Alpha，是项目的第一个版本，初期仅面向 Apple M4 Mac Mini。已实现的能力包括：实验性的 OpenGL 3.3 / OpenGL ES 3.0 支持（带 GPU 加速），桌面为KDE Plasma（运行在 Wayland 上）。
官方同时明确列出已知不可用的硬件功能：
· 休眠（suspend）不可用；
· USB-C 口无显示输出（HDMI 可用）；
· Thunderbolt / USB4 不可用；
· 功耗可能高于预期（桌面机型影响不大）；
· 出于安全考虑，扬声器最大音量被设了保守上限；
· 关机 / 重启不稳定（可以直接按电源键）。
官方表示：上述清单之外的功能均可工作且已测试。后续目标是扩展到其他 M4 / M4 Pro / M4 Max 设备，并已把 MacBook Neo 列入视野。项目方称只做了净室逆向工程（clean room reverse engineering），并希望最终所有工作都能进入上游 Linux 内核。
关注理由：① 先把「能跑」与「能日常」分开看。这份「不可用清单」本身比发布消息更有信息量：USB-C 无显示输出但 HDMI 可用，说明显示控制器的部分通路已经打通，而 Type-C 侧涉及的 DP Alt Mode / 复用器 / 电源域尚未接管；休眠不可用则几乎总是最晚被攻克的一项——它要求整个 SoC 的电源域、时钟、外设状态机都能正确保存与恢复，是「bring-up 完成度」最诚实的标尺。评估任何新平台支持度时，看它能不能休眠、能不能多屏，比看它能不能点亮屏幕靠谱得多。
② OpenGL 3.3 + Wayland + KDE Plasma 的组合，说明图形栈走的是「先可用后性能」路线。OpenGL 3.3 是一个刻意保守的基线——它足以驱动完整桌面环境，又不需要触碰 Mesa 中最激进的部分。先让桌面完全可用，再逐代追平硬件能力，这个顺序是正确且务实的。
③ LLM 参与内核与驱动 bring-up，已成为需要认真对待的工程变量。今天这条与 perf 改写、内核修复条目一起出现，构成了一个连续信号（详见本期第 6 条）。对我们的意义是：逆向 / bring-up 这类「大量样板 + 高确定性推理」的工作，正是当前模型收益最高的场景；而「架构取舍、时序边界、硬件勘误判断」仍必须由人负责。把任务按这个维度分类，比笼统讨论「AI 能不能写驱动」有用得多。

AMD BC-250 再获 Linux 支持推进：新补丁启用 PSP 安全处理器，让矿渣板可承担加密与 AI 负载
计算 compute 图形 GPU
AMD BC-250 是一块当初为加密货币挖矿设计的产品，基于精简版 Sony PlayStation 5 APU。它在 Linux 上正逐渐被重新利用，从通用计算到 AI 负载都有玩家在跑，形成了一个相当有意思的「第二人生」。本周末送出了最新一批 Linux 内核补丁。
硬件构成回顾：6 个 Zen 2 核心、24 CU 的 RDNA2 GPU、16GB GDDR6 显存。
本次的具体工作是三补丁系列，用于把 AMD PSP（Platform Security Processor，平台安全处理器）跑起来——需要给 AMD CCP（Crypto Co-Processor，加密协处理器）驱动做几处修改，才能让 BC-250 的安全处理器可用于加密任务。
该板卡的 Linux 支持此前已有积累：RADV 驱动补丁、AMDGPU 适配、传感器监控（Linux 6.15 hwmon）等。价格方面也颇为戏剧化：去年二手 BC-250 约 100 美元，而在眼下 PC 零部件价格暴涨的行情下，如今已涨到 200~350 美元。
关注理由：① 这是一个「软件生命周期比硬件生命周期长」的典型案例。BC-250 的原始用途（挖矿）已经消失，但硬件本身还在——16GB GDDR6 与 24 CU RDNA2 的显存/算力组合，在小显存 AI 推理与图形实验场景里仍有实用价值。让它重生的不是任何商业动机，而是开源栈的低门槛：只要有人愿意写补丁，一块被淘汰的板子就能获得新负载。这对我们的启示很直接——长期可维护的开源驱动，本质上是在给固定资产延长折旧年限。
② PSP 与 CCP 的启用是「可信计算能力」的开关。PSP 是 AMD 平台上的独立安全核，CCP 提供硬件加解密与压缩卸载。把这两个打通，意味着这块板子从「能算」变成「能安全地算」——可以跑加密任务，也是机密计算特性的前置条件。任何加速器平台，只要涉及多租户或数据保护，安全核与加密卸载是否可用都是必须尽早明确的一项能力，而不是等业务提出合规需求时才发现缺口。
③ 二手价格从 100 涨到 200~350 美元，说明社区驱动的「平价算力」需求真实存在。在整机与显卡价格高企时，被重新激活的老硬件会立刻被市场重新定价。这也提醒我们：软件支持度本身就是资产价值的一部分——上游支持越完整，硬件在二级市场的残值越稳。这一点在采购决策时值得写进评估模型。

2026 年内核红利实测：Linux 6.18 LTS → 7.3，AMD EPYC 服务器 100+ 项基准几何平均提速约 8%
计算 compute 内核 kernel
随着开发中的 Linux 7.3 在多个领域相较 7.2 表现出不错提升、Linux 7.2 又尤其为 I/O 带来明显收益，Phoronix 做了一次年度盘点式评测：衡量 2026 年至今 Linux 内核性能究竟进化了多少。
对比两端：Linux 6.18.52（2025 年底发布的 LTS）对 Linux 7.3 Git（截至 9 月 17 日）。
测试条件：相同硬件、相同 Ubuntu 26.04 LTS 基础系统；内核来自 Ubuntu Mainline Kernel PPA，便于独立复现与核对 Kconfig。
测试平台：单路 AMD EPYC 8635P「Sorano」服务器 —— 84 个 Zen 5 核心、6 × 64GB DDR5 内存、Kioxia KCD8XPUG1T92 PCIe Gen5 NVMe SSD。
测试规模：100 多项 Linux 服务器基准测试，结论是这一年确实出现了不少出色的内核性能优化，几何平均提升约 8%。
关于 LTS 归属还有一段悬念：Linux 7.3 稳定版将于 10 月下旬发布，可能成为今年的 LTS；但如果 7.3 与 7.4 都按期，7.4 会在 12 月底前发布，那么 2026 年的 LTS 就可能是 7.4——最终取决于 Greg Kroah-Hartman 的判定。
关注理由：① 「换内核免费拿到 8%」是极其便宜的性能。同一台服务器、同一套软件、同一份业务逻辑，仅更新内核就从 6.18 LTS 到 7.3 获得约 8% 的几何平均提升，而且没有引入新的硬件成本与调优风险。对比之下，靠业务侧优化拿 8% 通常需要大量人力。结论很直接：把内核升级纳入常规容量与成本规划，收益常常被严重低估。对大规模集群而言，8% 等价于把硬件采购预算相应削减一大块。
② 8% 的「几何平均」意味着改善是广泛而连续的，而非个别尖峰。几何平均对离群值不敏感——若只是某一两项基准暴涨，几何平均会被显著平缓化。所以这个数字反映的是一整年、上百项负载上的系统性累积：调度器、内存管理、I/O 路径、文件系统、网络栈各处各拿几个百分点。这类「均匀的进步」比单点突破更难获得，也更难被替代——它不是某一项优化的功劳，而是把每个默认路径都打磨了一遍。
③ 对性能评估方法论的参考价值。这次评测值得学习的地方在于可复现性设计：固定硬件、固定发行版基线、使用公开的内核 PPA 并公布 Kconfig。当我们要向团队或管理层论证某个平台收益时，「别人能照着复现」比「我测出来很快」重要得多。同时要注意评测的时间截面——这里用的是 7.3 Git 快照而非正式发布版，数字会随后续 rc 略有浮动，引用时应注明。

Linux perf script 大改：49 补丁砍掉内嵌 Python/Perl，改用 C 写的 Python 扩展模块，脚本从 3.7 秒降到 0.1 秒
计算 compute 内核 kernel
本周末送出的大补丁系列，重构了 Linux 内核 perf 子系统中的脚本化能力：移除内嵌的 Python 与 Perl 脚本支持，改为独立 Python 脚本 + 一个全新的 Python perf 模块。该模块是用 C 写的 Python 扩展（C extension module），性能远优于现状。
主导者是 Google 工程师 Ian Rogers。其动机是解决 perf script 长期存在的三个问题：开销高、构建依赖复杂、以及若干设计层面的困难。
效果非常直接：一段 Python 脚本原本需要 3.7 秒，改用独立脚本 + 新 perf 模块后只需 0.1 秒。
规模：共 49 个补丁，把 Python perf 代码迁移到新模块上，同时删掉基于 libpython 的旧代码与遗留 Python 脚本，整体约 2.1 万行代码的重构。Gemini 3.1 Pro 协助 Rogers 完成了这次改造。补丁目前正在 linux-perf-users 邮件列表上评审。
关注理由：① 37 倍提速的根因值得拆开看，而不只是记一个数字。原方案把 Python 解释器嵌进 perf 二进制，两者通过 libpython 反复跨界调用，每次采样都要跨越「C ↔ Python」边界，且解释器随 perf 一起构建与链接——这才是「开销高 + 构建依赖复杂」的真正来源。改成独立 Python 进程 + C 扩展模块后，边界只在顶层出现一次，热路径完全留在 C 与原生数据结构里。这是一个教科书级的取舍：不要把一个重量级运行时嵌进一个高频工具的主循环。
② 它顺带解决了「构建依赖」这个隐性成本。内嵌解释器意味着 perf 的构建必须依赖 libpython，于是内核工具的编译变得脆弱、与发行版 Python 版本强耦合。把依赖从「构建期」挪到「运行期」，是让工具能被更广泛环境编译与分发的有效手段——我们在做内部工具时也常遇到同样的纠缠：为了一点便利把重依赖塞进主程序，结果是 CI 与交叉编译环节长期不稳定。
③ 这已经是连续第 N 条「LLM 参与内核级改造」的信号。本期的 Gravity Linux（驱动 bring-up）、昨天的内核修复（error path cleanup）、以及这条 2.1 万行重构，都是同一个趋势在不同层面的体现：模型在「边界清晰、验证成本低、样板量大」的改造任务上收益最高——而「删掉一层间接」恰好属于此类。相应地，评审与验证环节的责任反而更重：当代码生成变快，瓶颈会明确地转移到「怎么快速确认它是对的」。这也是我们团队接下来要重点建设的能力。

「孤儿虚拟机」补丁提交评审：宿主机内核下线重启期间，虚拟机在专用物理核上继续不间断执行
计算 compute 内核 kernel
来自 Google 的一项相当引人注目的工作：为满足超大规模云厂商对零停机的追求，一组实验性补丁提出 「Orphaned VMs」（孤儿虚拟机）概念——让虚拟机在宿主机内核为了安全更新或重启而下线期间，继续不间断运行，配合 Live Update Orchestrator（LUO）完成。
核心思路是：孤儿虚拟机在被保留下来的物理 CPU 上持续执行 guest 指令，在整个宿主机重启期间完全与宿主操作系统及 VMM 解耦。实现这种「执行不对称性」的关键是引入 Caretaker（看护者）——一种运行在 hypervisor 特权硬件状态下的裸金属原语插入层，在宿主内核离线期间就地拦截并解决部分 VM exit。
所需机制包括：内存中的 vCPU 状态保存、物理 CPU 保留核心支持、片上调度框架，以及 KVM Caretaker Core 基础设施。
该 RFC 系列共 46 个补丁，已在 Intel、AMD、Arm 服务器处理器上测试过，但被明确称为「非常早期」的工作，尚不具备生产可用性。工作由 Google 的 Pasha Tatashin 主导。下个月在布拉格举行的 Linux Plumbers Conference 上会有进一步讨论。
关注理由：① 这解决的是一个真金白银的问题：内核安全更新的停机成本。宿主机打补丁重启，意味着其上所有虚拟机一起中断。对云厂商来说，这直接换算成 SLA 罚金与迁移开销。业界的常规解法是把虚拟机迁走再迁回来（live migration），代价是大量内存与网络带宽的搬运、以及迁移窗口内的性能抖动。「孤儿虚拟机」试图把这个成本压到接近零——不是搬走，而是就地续命。这两种路线的取舍是典型的工程权衡：迁移通用但昂贵，就地保活便宜但机制复杂得多。
② 「Caretaker 裸金属原语插入层」这个设计很值得琢磨。难点在于：宿主内核不在时，原来由内核承担的 VM exit 处理没有执行者。解决办法是在 hypervisor 特权态里放一个极简的、只负责必要裁决的层，把能本地解决的 exit 就地解决，解决不了的再挂起等待。这里体现的原则很清晰——关键路径上的组件应当尽可能小、依赖尽可能少，因为它必须在宿主环境完全不可用时仍然独立正确运行。我们设计带外管理、固件、或任何「降级仍须可用」的模块时，都应该按这个标准约束自身的复杂度。
③ 需要点名的工程难点：时间基准、游离中断、guest 间 IPI。摘要里提到的时间漂移（timekeeping drift）尤其微妙——宿主内核离线期间，虚拟机感知的时间从哪来？这直接关系到 guest 内的定时器、超时、日志时序与加密协议的有效期判断，处理不当会造成难以复现的诡异故障。凡是引入「局部系统独立运行」的设计，时钟与中断这两件事都要提前设计，而不是留到 bug 阶段。这也是评估任何 live update / 故障隔离方案时，最该追问的两个问题。
