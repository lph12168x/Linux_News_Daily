Nouveau 获得 HDMI Deep Color 补丁：开源 NVIDIA 驱动开始支持 10/12/16 位色深，暂仅 RGB（无 YCbCr）
显示 display 图形 GPU
开源 NVIDIA 内核图形驱动 Nouveau 收到一组新补丁，用于启用 HDMI Deep Color（深色）支持。Deep Color 允许每色通道以 10 位、12 位或 16 位表示——相比常规的 8 位，能显著减少色带（banding）与渐变断层，是 HDR 与高色深显示链路的基础能力之一。
值得注意的两点：
· 这批补丁据称是在「AI 伙伴（AI partners）」协助下完成的；
· 定位上，Nouveau 仍是在 Nova 驱动达到可用状态之前，承担开源 NVIDIA Linux 支持的主力内核驱动。
当前限制也很明确：
· 仅支持 RGB 输出，暂不支持 YCbCr 色彩空间；
· 16 位/通道这一档尚未在具备该能力的显示器上实测过。
补丁已发到 dri-devel 邮件列表（2026-09-22 提交）公开评审。
关注理由：① 色深（bpc）是显示链路上最容易被忽视、又最影响观感的一环。8 位色深在平滑渐变（天空、烟雾、肤色过渡、暗部）上必然出现色带，专业显示与 HDR 场景对此极其敏感。Deep Color 把每通道提升到 10/12 位，本质上是把量化误差压到人眼阈值以下。对做显示栈的人来说，这里有一条常被混淆的账：「色深」与「色彩空间」是两件独立的事——补丁同时支持 RGB 与 YCbCr 才算完整，因为视频内容天然是 YCbCr 4:2:0，若链路只走 RGB，就得在中间做一次转换，既引入额外带宽也引入额外误差。这次「仅 RGB」的限制，会直接影响它在影音场景的实用性。
② 16 位这条路为什么最难，值得留意。10/12 位在 HDMI 的 TMDS 带宽预算里已有成熟做法（靠 FRL 高码率或降刷新率换取）；16 位/通道则要求整条链路——GPU 输出格式、时序参数、链路码率、接收端能力——全部对齐，任何一环缺失就退化。补丁作者标注「未在支持 16 位的显示器上测过」，正是这种端到端依赖的真实写照。评估任何显示特性，都不能只看发送端支持与否，必须把「是否有接收端能验证」当成前置条件。
③ 这是「Nouveau 与 Nova 双轨并行」策略的又一例证。上游一边推进全新的 Nova（Rust 重写）驱动，一边继续给 Nouveau 打补丁补齐显示能力，说明过渡期会相当长，而存量用户的实际体验不能被搁置。换到我们自己的平台看，同样的道理成立：新架构推进期间，旧栈的维护投入不是成本，而是让新栈可以从容成熟的缓冲。这条经验对 RDMA 栈的代际切换同样适用。

Collabora 提出 VRR「目标帧率限制器」uAPI：让用户态指定刷新率区间或固定靶点，并新增 QMS 连接器属性
显示 display 内核 kernel
Collabora 的 Nicolas Frattaroli 发出一组 RFC 补丁（共 25 个），提议为 Linux 桌面引入一套新的用户态 API（uAPI），用于为可变刷新率（VRR，Variable Refresh Rate）机制指定帧率目标。
提案内容：
· 用户态（游戏 / 应用 / 合成器）可以指定 VRR 工作的受限区间（constrained range）；
· 或指定一个固定靶点（fixed target）；
· 另新增一个 QMS（Quick Media Switching，快速媒体切换）连接器属性。
提案动机（作者原话要点）：为回避现实世界的不完美，通过把 VRR 约束在有限区间或固定点，可以在预期帧率范围内获得无卡顿（judder-free）或低延迟的呈现，同时避免跌入会引起可见亮度闪烁的刷新率区间。QMS 的加入则让连接器能提前向接收端预告即将发生的刷新率变化，适用于媒体播放场景——这样电视等设备端的高级图像处理算法就不必为了「随时能全帧率切换」而被整体关闭。
实现范围：补丁为 HDMI state helpers 实现了「Game Mode」VRR，并在 Rockchip RK3588 驱动上做了落地实现。配套还有一份针对 Wayland 参考合成器 Weston 的 vrr-limiter 分支。该议题也在今年的 Display Next Hackfest 上做过讨论。
关注理由：① 这条精准命中 VRR 的真实痛点：低刷新率区间的亮度闪烁。VRR（FreeSync / Adaptive-Sync）的理想叙事是「刷新率跟随帧率，消除撕裂与卡顿」；但现实中面板在刷新率过低时（常见于 40Hz 以下）会出现背光/驱动上的亮度波动，这就是玩家抱怨的 VRR flicker。厂商的常规做法是在面板端设一个 LFC（Low Framerate Compensation）下限或用各种 workaround。这套 uAPI 把「可用区间」这件事从「面板/驱动隐藏兜底」提升为「用户态可显式声明的契约」，是接口设计理念上的一步——把隐含假设变成显式协议。
② 「固定靶点 + QMS 预告」是两件不同性质的能力，不要混为一谈。固定靶点解决的是呈现侧问题：内容帧率稳定时，让 VRR 钉在某个刷新率上换取最彻底的稳定；QMS 解决的是链路侧问题：切换刷新率需要时间，接收端（电视）如果不知道要切换，就会用保守的处理模式导致黑屏或重新握手的延迟。QMS 的价值在于把「即将变化」这件事提前告知，从而让接收端可以在切换前夕退出激进处理。任何涉及「动态改变链路参数」的设计——无论是刷新率、编码参数还是链路码率——提前通告（look-ahead signaling）几乎总是比事后补偿便宜。这与我们在 RDMA 上做拥塞通知、在 PCIe 上做链路重训练预告的思路是同一类。
③ 落点选在 HDMI 与 RK3588 上，透露了该特性的优先场景。HDMI 走的是消费电视 / 媒体播放路径，RK3588 是嵌入式 / 媒体盒子主力 SoC——两者都指向「影音消费链路」而非游戏桌面，与 QMS 的媒体播放定位一致。这也说明：一个 uAPI 的架构中立性，最终要看它先在哪条最痛的链路上落地；先落地者会反向塑造接口细节。做跨平台接口设计时，这个问题值得提前想清楚。

ZLUDA 用 hipFFT 实现部分 NVIDIA cuFFT API：Stock Folding@Home 的 CUDA 核心已能在 AMD 显卡上跑起来
计算 compute 图形 GPU
开源项目 ZLUDA——目标是让 CUDA 应用跑在非 NVIDIA GPU（尤其 AMD Radeon）上——现已实现对 NVIDIA cuFFT 部分核心 API 的支持。cuFFT 是 NVIDIA 的 GPU 加速快速傅里叶变换（FFT）库。
实现方式：由开源开发者 「AmosKito1」完成，思路是把 cuFFT 动态翻译到 hipFFT——hipFFT 是 AMD ROCm / HIP 生态中对应的 FFT 库。相关 PR 为 ZLUDA #672。
覆盖范围有明确边界：并非全部 cuFFT API 都支持，只覆盖存在直接 hipFFT 等价接口的那部分——这是「有限映射」而非「完整仿真」。
实际效果：这一层翻译已经足以让原版（stock）Folding@Home 的 Core24 与 Core27 CUDA 计算核心在 AMD 硬件上正常运行。Folding@Home 是著名的分布式蛋白质折叠计算项目，其计算核心长期只提供 CUDA 版本。
该支持已包含在 ZLUDA 7-preview.11 版本中。
关注理由：① 「只做等价映射」是一个诚实且可持续的工程边界。CUDA 到非 NVIDIA 平台的迁移至少有三种路线：源码级移植（改代码，最干净但成本高）、API 翻译层（ZLUDA / HIPIFY 这一类）、完整仿真（最通用但性能与维护都不可接受）。ZLUDA 明确选择中间路线，并且只在语义等价处建立映射，映射不了的地方就直接不支持。这个取舍极其重要：伪支持比不支持更危险——它会让应用「跑起来但结果静默错误」。科学计算类负载（FFT、BLAS、求解器）对数值正确性零容忍，宁可在加载期报错，也不能在结果上悄悄出错。
② FFT 是「最后一道硬骨头」之一，它被打通意味着应用可用面显著扩张。在 CUDA 生态里，真正难以绕开的其实不是运行时本身，而是那些被科学计算与工程软件深度依赖的数值库：cuBLAS、cuFFT、cuSPARSE、cuSOLVER 等。其中 FFT 之所以关键，是因为它是大量上层算法的基础组件——信号处理、成像重建、量子化学、分子动力学、深度学习中的卷积加速都直接或间接依赖它。只翻译 API 而不翻译这些数值库，等于只修了门框没装门。这条进展的实际意义，比它表面上「一个库的补丁」大得多。
③ 对异构计算选型的启示：生态锁定的机制值得拆解。CUDA 的护城河并不主要在硬件性能，而在于「应用 → 数值库 → 运行时 → 硬件」这条完整链条上每一层都被默认绑定。ZLUDA 这类项目的价值，在于逐层测量这条链条到底有多少层是不可替换的——每打通一层，就为多厂商/多硬件路线打开一扇门。如果我们在自研加速器上要承接既有生态，同样应该先做这件事：把目标应用的实际调用面逐层枚举出来，统计哪些 API、哪些数值库、哪些编译产物形式被真正用到，而不是笼统地讨论「兼容 CUDA 有多难」。这个枚举本身就是最有价值的可行性结论。

Strix Halo 实测 Linux 7.2 vs 7.3：图形基本持平、NUMA 大幅改善，llama.cpp Vulkan 后端略快
计算 compute 图形 GPU
上周刚测过 Ubuntu 26.10 上 Ryzen AI Max+「Strix Halo」的性能提升，随后 Canonical 把 Ubuntu 26.10 的内核从 Linux 7.2 切到 Linux 7.3，Phoronix 于是补做了两者在同一台机器上的对照评测。
测试平台：Framework Desktop，AMD Ryzen AI Max+ 395，集成 Radeon 8060S Graphics。
主要结果：
· 图形基准基本持平——GravityMark（Vulkan 与 Vulkan 光追）下 Linux 7.2 更快，DDraceNetwork（6144×2560、Vulkan）下 Linux 7.3 略有改善；
· NUMA 性能改善明显（Stress-NG NUMA 测试），与此前 EPYC 服务器上观察到的大幅 NUMA 提升相呼应；
· Stress-NG 的 MEMFD、Mutex、CPU Cache、Socket Activity 等子项均有提升；ctx_clock 上下文切换也有改善；
· 网络延迟略降（ethr TCP latency），与其他系统测试趋势一致；
· 视频编码 uvg266 / x265、内核编译、llama.cpp Vulkan 后端（Qwen3.5-9B-Q8_0 提示处理）上 7.3 更快；
· 也有反向项：NAMD（STMV 106 万原子）、ClickHouse、llama.cpp CPU BLAS（gpt-oss-20b）下 7.2 更快。
总体结论：在数十项真实负载上，7.3 相对 7.2 差异不大——但 Linux 7.2 本身已让 Ubuntu 26.10 相对 Ubuntu 26.04 LTS（Linux 7.0）表现出可观提升。
关注理由：① 「差异不大」本身就是有价值的结论，不要只盯着提升项。当一个内核从 7.2 到 7.3 在成熟平台上几乎无差异时，正确的解读是：这个平台的支持已经进入稳态，新一代内核的改动主要落在别处（新硬件、新特性、NUMA/I/O 等结构性路径）。反过来，如果每次小版本升级都在常见负载上出现大幅波动，那才是需要警惕的信号——说明测试覆盖不足或存在未稳定路径。把「无回归」当作一项独立的验收标准，比只追提升项更专业。
② NUMA 改善的连续性，说明这是本轮内核的一条主线。从 09-22 的 EPYC 盘点（100+ 项基准几何平均 +8%）到这次 Strix Halo，NUMA 相关路径在两代差异极大的硬件上都出现改善。这种「跨平台可复现的结构性收益」比单机型数字可信得多，也是我们评估内核收益时最该优先采信的形态——它意味着改动打在了公共路径上，而非某个平台的特定勘误。对 AI 推理这类内存带宽敏感、且常跑在统一内存架构上的负载，NUMA 与内存放置策略的收益往往被低估。
③ llama.cpp 的「Vulkan 快、CPU BLAS 慢」这一组对比很值得琢磨。同一版本内核、同一台机器，GPU 后端走 Vulkan 转好，CPU 后端走 BLAS 转差，说明 7.3 的收益是路径相关而非全局的——很可能来自调度、内存放置或驱动侧对 GPU 提交路径的改善，而 CPU 侧的 BLAS 计算更多受制于线程调度与缓存行为的细微变化。这提醒我们：「换内核提速 X%」这类结论必须绑定具体执行路径（GPU 还是 CPU、哪种后端、哪种数据布局），否则引用到生产环境会大幅失真。评估自身 AI 推理栈时，也应按「后端 × 负载 × 数据布局」三个维度分别建基线，而非只看一个总分。

Cache Aware Scheduling 修复批次进入 tip/sched/urgent：将随 Linux 7.3 提交并回移 7.2，瞄准 LLC 亲和与热插拔正确性
计算 compute 内核 kernel
Cache Aware Scheduling（CAS，缓存感知调度）自 Linux 7.2 进入主线后，一直在修复中。最新一轮修复本周内将合入 Linux 7.3，并标记回移（backport）到 Linux 7.2。
这批工作由 Intel 工程师 Tim Chen 主导，核心是让 CAS 的「把相关任务聚到共享最后一级缓存（LLC）的核上」这一目标能够真正生效——CAS 的收益来自更好的缓存局部性与更低延迟，避免潜在的缓存抖动（cache bouncing）开销，前提是 bug 不从中作梗。
本次修复的内容：
· 让 nr_pref_llc_running 保持在 runnable domain 内（不越界漂移）；
· 在主动负载均衡（active load balance）中遵守 migrate_llc_task 的语义；
· 在 CPU 热插拔（hotplug）时刷新 LLC 容量信息——避免拓扑变化后仍用过期数据做决策；
· 跳过内核线程（kernel thread）参与缓存感知调度；
· 以及若干其他底层调整。
补丁已合入 tip/tip.git 的 sched/urgent 分支。由于进入的是 TIP 的 urgent 分支，预计本周内提交给当前的 Linux 7.3 周期；全部补丁同时标记回移 Linux 7.2。此前本周期还修过 CAS 在混合 CPU（hybrid）上的问题。
关注理由：① 这批修复的共性很清晰：拓扑信息的「时效性」与「作用域」。四条主要修复里有两条（LLC 容量随热插拔刷新、nr_pref_llc_running 不越出 runnable domain）本质是同一类错误——调度决策依赖的拓扑/状态数据，在某些事件后不再有效，或作用范围被错误地放大。这类 bug 的典型特征极其难查：平时完全正常，只在热插拔、CPU 离线、容器绑核、或特定核数组合下偶发，而且表现为性能退化而非功能错误，因此很难被功能测试捕获。我们在自己的调度与资源管理代码里，应当把「什么事件会让缓存下来的拓扑信息失效」列成一张显式清单，而不是依赖开发者的记忆。
② 「进 urgent 分支 + 标记回移」的流程信息比修复本身更值得记录。走 sched/urgent 而不是正常的 merge window，意味着维护者判定这是必须尽快修复的正确性/性能缺陷，值得承担破坏 rc 稳定性的风险；同时标记回移 7.2 说明问题是在 7.2 引入的，受影响用户已经存在于生产环境。这个组合本身就是一份清晰的「严重性评级」。对于在生产环境跑 7.2 的团队，这是明确的升级/打补丁信号，而不是可以排进下一季度再看的优化项。
③ 从工程角度看，「新特性引入 → 关联路径回归 → 多轮修复」是常态节奏，而不是失职。CAS 从进入主线（7.2）到反复修（7.2 回移 + 7.3 混合 CPU 修复 + 本次热插拔/负载均衡修复），只用了很短时间。真正值得注意的是修复的方向：从「功能不正确」逐步收敛到「边界条件与拓扑变化」。评估任何新调度/资源管理特性的成熟度，看的正是这个收敛速度——如果连续多轮修复都还在改主逻辑，说明设计未定型；如果很快转入热插拔、混合拓扑、越界保护这类边缘场景，说明主干已经稳了。这个判断方法可以迁移到我们平台上的任何调度特性评审。

Linux 新增 AMD SEV 状态查询接口：sysfs 暴露 sev_status，免去 sevctl/snpguest 等用户态工具
计算 compute 内核 kernel
一项令人意外地直到现在才被加入的便利功能即将进入内核：新的 sysfs 接口 /sys/devices/system/cpu/sev/sev_status，用于上报 AMD SEV（Secure Encrypted Virtualization，安全加密虚拟化）的状态。
实现细节：补丁已排队进入 tip/tip.git 的 x86/sev 分支，目标为 Linux 7.4（该周期将于 10 月开启）。该文件将上报客户虚拟机（guest VM）中 SEV_MSR 寄存器的状态。
价值：有了它，判断 SEV 虚拟机的加密状态不再需要借助 sevctl、snpguest 之类的用户态工具——直接读一个 sysfs 文件即可。
信息密度：SEV_STATUS 这个 MSR 不只反映「SEV 是否启用」，其高位还能指示当前生效的能力，例如 SEV-ES（加密状态保存）与 SEV-SNP（安全嵌套分页）是否处于活动状态。
对应提交为 tip 树中的 250ee734115bca1c1f7a38d838909aa83cce87ae。
关注理由：① 「状态可观测性由用户态工具下沉到内核 sysfs」是一个反复出现的正确方向。用 sevctl / snpguest 这类外部工具判断状态有三个固有缺陷：需要在 guest 内安装额外软件（在最小化镜像、容器、不可变系统里很麻烦）、工具版本与内核特性可能脱节、结果无法被系统软件的通用采集链路（监控 agent、编排平台、合规扫描）直接拿到。而 sysfs 是统一、稳定、无需额外依赖的可观测面。这个模式在过去几年里反复被验证：CPU 特性、频率、拓扑、显存用量（如本期前后的 DRM memstat 提案）都在向 sysfs/标准节点收敛。当一项能力需要靠「装个工具去问」才能知道时，它一定会在自动化环境里被漏掉。
② 读 MSR 而非「读一个布尔值」，说明设计者理解能力组合的复杂性。机密计算的能力不是一个开关，而是一组按代际叠加的特性：SEV 基础加密 → SEV-ES（寄存器状态也加密，防止 hypervisor 在异常/中断时窥探）→ SEV-SNP（增加内存完整性保护与证明）。不同的上层安全方案对能力下限的要求完全不同——只支持 SEV 与支持 SEV-SNP 在威胁模型上有实质差别。直接暴露位域而不是替用户归纳成一个「已加密/未加密」的结论，把判断权留给策略层，这是正确的接口粒度。做安全与虚拟化相关接口时，过早地做「友好归纳」往往会丢失关键信息，事后只能靠加新接口补救。
③ 对机密计算与加速器直通的直接关联。结合此前 AMD 的 SEV-TIO / TDISP 方向（PCIe 6.0 下的机密计算设备直通），可以看到一条越来越清晰的链路：设备侧的可信直通，必须以平台侧可信状态的完整可观测性为前提。要验证「这台虚拟机是不是真的处于受保护状态、挂给它的设备是不是真的走加密路径」，就必须能在运行时逐项查验每一层的能力位，而不是靠启动参数推断。我们如果要在自研加速器上支持类似场景，对应的状态上报节点应当与加密路径同期设计，而不是等业务提出合规需求时再补——补出来的接口通常既不够用、也无法覆盖早期硬件的差异。

systemd 262 发布：内置内存态 unit 作为兜底、可编成静态单二进制 PID 1，并为未经评审的 AI/LLM 代码加「金丝雀」
内核 kernel 计算 compute
systemd 262 正式发布，作为一次特性更新，延续了「功能密集」的风格。主要变化：
· 内置一组基础 unit 文件：当磁盘上的 unit 无法加载、或在未安装任何 unit 文件的容器中运行时，systemd 会回退到这些内存态兜底定义（涵盖 reboot / shutdown target、systemd-poweroff 服务、multi-user target）；
· 可作为静态链接的单一 PID 1 / executor 二进制构建，面向极小型容器；
· NUMAPolicy= 现在接受 preferred-map 与 weighted-interleave 两种取值；
· service unit 新增 LUOSession= 选项，可由 systemd 创建 Live Update Orchestrator（LUO）会话，并伴随一批 LUO 集成改进；
· systemd-firstboot 支持 systemd.firstboot=headless，抑制全部交互提示、走非交互自动配置，服务无人值守安装；
· systemd-coredump 支持 Linux 6.17 引入的内核 coredump socket 协议；
· systemd-homed 新的 FSCRYPT 后端家目录默认使用 FSCRYPT v2 策略；
· systemd-cryptenroll 新增首次启动注册向导；
· systemd-vmspawn 的 --coco= 选项在原有 AMD SEV-SNP 之外，新增支持 Intel TDX；
· 新增 dm-clone 启动集成；
· 以及最受关注的一项——携带 用于检测未经评审的 AI/LLM 代码贡献的「AI 金丝雀（AI canary）」。
完整变更列表见 GitHub 上的 v262 发布说明。
关注理由：① 「AI 金丝雀」这件事的意义远超 systemd 本身。注意这里的关键词是「未经评审（un-reviewed）」，而不是「AI 写的」。这一定位很精准：真正的问题从来不是代码由谁生成，而是它有没有经过有效的人工审查。当生成成本趋近于零时，评审环节会成为唯一的质量闸门，也会成为第一个被流量淹没的环节。systemd 作为最核心的用户态基础设施，率先把这件事机制化，等于承认了一个现实：上游的评审带宽已经无法匹配提交量，需要技术手段来标记风险面。对我们的直接启示是——团队应该主动统计「AI 生成代码在合并前的评审覆盖率」，而不是笼统地表态支持或禁止 AI 编程。这个指标才是可管理、可改进的。
② 与昨天的「孤儿虚拟机」补丁合起来看，Live Update 这条线正在成形。本期 LUOSession= 让 systemd 能创建 Live Update Orchestrator 会话，而 09-22 期记录的「孤儿虚拟机」46 补丁正是让宿主机内核下线期间虚拟机不间断执行。两者是同一个目标的两端：内核/系统需要「在线替换自己」的机制，而上层需要一个编排者来协调这场替换。这类跨越内核与 init 系统的协同设计，恰恰是「零停机运维」从概念走向可部署的关键一步——单靠任何一侧都无法完成。跟踪这条线的推进会比跟踪单个补丁更有价值。
③ 「内存态兜底 unit + 静态单二进制 PID 1」瞄准的是容器与不可变系统。这两个特性合起来解决同一个问题：在「没有传统根文件系统」的环境里，init 系统必须能自给自足。对于最小化容器镜像、initramfs、以及资源极受限的嵌入式场景，少掉一层「必须预先安装配置文件」的依赖，就等于少掉一整类启动失败。这与本期第 1 条（Nouveau 给 Deep Color 补丁）、第 6 条（SEV 状态下沉 sysfs）共享同一思路：把「必须依赖外部预先准备」的东西内化，让系统在更恶劣的条件下仍能正确启动与自描述。这个方向对需要在裁剪环境中部署加速器驱动的场景尤其相关。

SPECviewperf 15.0.1 Linux 原生版发布：终结 Linux 侧落后 Windows 一年多的局面，x86_64 与 AArch64 双架构可用
图形 GPU 显示 display
SPEC 发布了 SPECviewperf 15.0.1 的 Linux 原生版本——这是这一业界标准工作站图形基准测试在 Linux 上的补位。
背景：SPECviewperf 15 早在 2025 年 5 月发布，但当时只提供 Windows 版本，Linux 支持再次滞后。今天 Linux 终于追上。
版本跨度：15.0.1 相对此前 Linux 上的 SPECviewperf 2020 是一次大幅更新。
架构支持：该 Linux 构建提供 x86_64 与 AArch64 两种版本。
关键差异（重要）：
· Windows 版 SPECviewperf 15 增加了 DirectX 12 与 Vulkan 图形 API 支持；
· 而 Linux 版 15.0.1 目前只支持 OpenGL 4.5。
Phoronix 表示接下来会用 SPECviewperf 15.0.1 Linux 做一批工作站 GPU 与驱动对比基准。详细说明见 SPEC.org 的 GWPG 页面。
关注理由：① 先看「补齐了什么」，再看「还缺什么」——后者往往更说明问题。这次发布的实质价值是把 Linux 工作站基准从 SPECviewperf 2020 拉到了 15.x 世代，让 Linux 侧的评测结论重新具备可对比性。但「Linux 版仅 OpenGL 4.5，Windows 版有 DX12 + Vulkan」这一条差异，才是更值得关注的信号：它说明商业基准套件的投入顺序仍然跟随 Windows 专业软件生态，而 Linux 上的工作站用户长期只能在「降级的测试集」上做对比。对采购与评估工作的直接影响是：用 Linux 版 SPECviewperf 测出的相对排名，不能直接套用到 Vulkan/DX12 路径的结论上——这两条路径在驱动里的实现、优化成熟度、乃至已知勘误都完全不同。
② 基准工具的「版本对齐」本身就是一项基础设施，值得作为独立事项管理。当测试工具与目标软件的世代脱节时，会产生一个隐蔽问题：测出来的性能变化无法归因——到底是硬件/驱动变了，还是测试负载变了？这次 Linux 版一次性从 2020 跨到 15.0.1，历史基线数据会全部失效，必须重建。凡是依赖长期基准做容量规划或回归监控的团队，都应当把「基准套件版本 + 负载版本」当作基线元数据的一部分记录下来，否则跨版本对比得出的结论都是不可靠的。
③ AArch64 版本的存在，说明 Linux 工作站场景正在向 ARM 延伸。SPECviewperf 的 Linux 版同时提供 x86_64 与 AArch64，这不是顺手的交叉编译，而是对应了真实需求——ARM 工作站（如各类基于 Grace、Ampere、以及国产/自研 ARM 平台的图形工作站）在专业图形场景的份额在上升。对做图形/显示驱动的团队而言，这意味着专业图形这套负载组合（大体量模型、复杂着色、高精度几何）将逐渐进入 ARM 平台的验证清单，而这类负载对显存带宽、驱动成熟度、以及 OpenGL 兼容层的压力，都远高于消费级游戏基准。提前把这类真实专业负载纳入平台验收路径，比只看合成基准更有指导意义。
